1️⃣ Aufgabe 1: Eine Klasse für komplexe Zahlen (Version 1 – öffentlich)

Komplexe Zahlen bestehen aus Realteil und Imaginärteil (kartesische Form): z = a + b·i. Wir modellieren das als Klasse ComplexNumber mit zwei double-Datenelementen.

Schritt 1 – Klassendeklaration: Erzeugen Sie eine Datei complexnumber01.h mit folgendem Inhalt:

cpp
#pragma once

class ComplexNumber
{
public:
    double mReal;
    double mImag;
};

Schritt 2 – Hauptprogramm: Erzeugen Sie eine Datei part01.cc mit der freien Funktion int main() – genau eine Datei pro Projekt darf sie enthalten:

cpp
#include <iostream>
#include "complexnumber01.h"

int main()
{
    ComplexNumber cn1;
    std::cout << "cn1[" << cn1.mReal << "," << cn1.mImag << "]"
              << std::endl;

    const ComplexNumber cn2{1.0, 2.0};
    std::cout << "cn2[" << cn2.mReal << "," << cn2.mImag << "]"
              << std::endl;
}

Schritt 3 – Übersetzen und starten: Nutzen Sie die Ein-Datei-Methode aus Blatt 02: part01.cc öffnen, dann Strg+Shift+B. Danach starten Sie im eingebauten Terminal.

🪟 Windows:

bat

🍎 macOS / 🐧 Linux:

bash
./part01
⚠️ ACHTUNG – die Compiler-Falle: Falls das Dropdown (oder der erste ▶-Klick) „C/C++: cl.exe build active file" anbietet: NICHT wählen – cl.exe ist der Microsoft-Compiler und funktioniert nur in speziellen VS-Terminals (Fehler: 'cl.exe' is not recognized). Immer die g++-Variante wählen! Ab Aufgabe 2 pinnt Ihre eigene tasks.json den g++-Build fest.

Schritt 4 – Beobachten und notieren:

  • Was gibt die Zeile mit cn1 aus – und warum? (Stichwort: die Datenelemente wurden nicht initialisiert.)
  • Welchen Nachteil hat es, dass die Datenelemente öffentlich sind – und dass jeder sie von außen beliebig lesen und schreiben kann?
📖 INFO: Der Compiler warnt Sie bereits: g++ meldet mit den Warn-Flags etwa 'cn1.ComplexNumber::mReal' is used uninitialized. Genau für solche Meldungen lohnt sich der rote Wellenstrich und die Problems-Ansicht (Strg+Shift+M) aus Blatt 02.

2️⃣ Aufgabe 2: Initialisierungen (Version 2 – mit Initialisierern)

Die erste Version ist fehlerhaft – die Objekte starten mit unbestimmten Werten. Diskutieren Sie mögliche Gründe! Dann beheben wir das.

Schritt 1 – Verständnisfragen (beantworten Sie schriftlich, als Kommentarblock in part02.cc):

  • Was versteht man unter Standard-Initialisierung für primitive Datentypen in C++?
  • Welche Arten der Initialisierung von Datenelementen einer Klasse existieren? (Tipp: in-class-Initialisierer in equal-Form = 0.0 und in brace-Form {0.0}.)

Schritt 2 – Header mit Initialisierern: Erzeugen Sie complexnumber02.h – die Klasse erhält jetzt in-class-Initialisierer und einen Konstruktor:

cpp
#pragma once

class ComplexNumber
{
public:
    ComplexNumber() = default;
    ComplexNumber(double real, double imag);

    double mReal = 0.0;  // equal-Form
    double mImag{0.0};   // brace-Form (besser!)
};

Schritt 3 – Konstruktor-Definition: Erzeugen Sie complexnumber02.cc – die Definition steht außerhalb der Klasse und nutzt die Initialisierungsliste:

cpp
#include "complexnumber02.h"

ComplexNumber::ComplexNumber(const double real, const double imag) :
    mReal{real}, mImag{imag}
{
}

Schritt 4 – Hauptprogramm: Erzeugen Sie part02.cc (Kopie Ihrer main() aus Aufgabe 1 – diesmal mit #include "complexnumber02.h"):

cpp
#include <iostream>
#include "complexnumber02.h"

int main()
{
    const ComplexNumber cn1;
    std::cout << "cn1[" << cn1.mReal << "," << cn1.mImag << "]"
              << std::endl;

    const ComplexNumber cn3{4.0, 5.0};
    std::cout << "cn3[" << cn3.mReal << "," << cn3.mImag << "]"
              << std::endl;

Schritt 5 – tasks.json für zwei Dateien: Ab jetzt besteht das Projekt aus part02.cc und complexnumber02.cc – der Ein-Datei-Task aus Blatt 02 reicht nicht mehr (sonst: Linker-Fehler undefined reference to ...). Erzeugen Sie den Ordner .vscode (mit führendem Punkt!) und darin die Datei tasks.json – voller Pfad: progcpp-ubungen\uebung03\.vscode\tasks.json (relativ zum geöffneten Ordner also .vscode\tasks.json):

json

    "tasks": [
        {
            "type": "cppbuild",

Danach: Strg+Shift+B – VS Code nimmt den Default-Task mit beiden Dateien. Starten wie in Aufgabe 1.

🧠 MERKE: Genau eine Datei darf int main() enthalten. Header (.h) kommen nicht in args (sie wirken über #include). Wildcards wie ${workspaceFolder}/*.cc funktionieren mit dem MSYS2-g++ (getestet: g++ 15.2.0 expandiert sie) – aber Vorsicht in diesem Workspace: part01.cc, part02.cc und part03.cc enthalten je ein main(). Ein Wildcard würde alle drei einsammeln und mit „multiple definition of main" abbrechen. Deshalb: Dateien pro Task explizit listen.

Schritt 6 – Beobachten: Jetzt ist auch cn1 korrekt initialisiert – die Warnung von Aufgabe 1 ist verschwunden.

✅ So sieht Erfolg aus: part02 läuft und gibt cn1[0,0] und cn3[4,5] aus. Sie können die drei Initialisierungsarten benennen und erklären, warum = default zusammen mit den in-class-Initialisierern hier nötig ist.

3️⃣ Aufgabe 3: Kapselung (Version 3 – private + Beobachter)

Schritt 1 – Header mit Kapselung: Erzeugen Sie complexnumber03.h – die Datenelemente werden jetzt private, der Lese-Zugriff erfolgt über Beobachter-Elementfunktionen:

cpp
#pragma once

class ComplexNumber
{
public:
    ComplexNumber() = default;
    ComplexNumber(double real, double imag);

    double real() const;
    double imag() const;

private:
    double mReal = 0.0;
    double mImag{0.0};
};

Schritt 2 – Definitionen: Erzeugen Sie complexnumber03.cc – Konstruktoren und Beobachter-Definitionen (alle außerhalb der Klasse):

cpp
#include "complexnumber03.h"

ComplexNumber::ComplexNumber(const double real, const double imag) :
    mReal{real}, mImag{imag}
{
}

double ComplexNumber::real() const
{
    return mReal;
}

double ComplexNumber::imag() const
{
    return mImag;
}

Schritt 3 – Hauptprogramm: Erzeugen Sie part03.cc – Ihre main() nutzt jetzt die Beobachter statt der Datenelemente:

cpp
#include <iostream>
#include "complexnumber03.h"

int main()
{
    const ComplexNumber cn1;
    std::cout << "cn1[" << cn1.real() << "," << cn1.imag() << "]"
              << std::endl;

    const ComplexNumber cn2{1.0, 2.0};
    std::cout << "cn2[" << cn2.real() << "," << cn2.imag() << "]"
              << std::endl;
}

Schritt 4 – tasks.json erweitern: Ergänzen Sie in .vscode/tasks.json einen zweiten Task mit eigenem label (z. B. "C++ build part03") und den Dateien part03.cc + complexnumber03.cc – analog zu Aufgabe 2, Schritt 5. Umschalten über „Terminal → Run Build Task…" (Strg+Shift+B).

Schritt 5 – Fehler provozieren (wichtig!): Versuchen Sie in part03.cc einmal, direkt auf cn2.mReal zuzugreifen (alte Zeile aus Aufgabe 1). Übersetzen – g++ meldet exakt:

text
error: 'double ComplexNumber::mReal' is private within this context

Das ist der Beweis der Kapselung – genau so soll es sein. Zeile zurückbauen.

Schritt 6 – Verständnisfragen:

  • Warum müssen real() und imag() mit const qualifiziert werden? (Tipp: cn2 ist ein const-Objekt.)
  • Was gewinnen wir durch private – obwohl der Code jetzt länger ist?
✅ So sieht Erfolg aus: part03 läuft (cn1[0,0], cn2[1,2]), der private-Zugriff-Test liefert den erwarteten Compilerfehler, und Sie können const-Korrektheit bei Beobachtern erklären.
