2. Zeiger: Zeiger-Variablen, Zeiger-Werte und Ziel-Objekte

Achtung: Java-Programmierer!

In einigen Lehrbüchern und vielen Web-Quellen werden Java-Referenzen und C++-Zeiger fast gleichgestellt. Manche Quelle vergleichen sie sogar mit C++-Referenzen.

Obgleich die meisten C++-Compiler Referenzen, d.h. die Verbindung von Namen zu Objekten mit Hilfe von Adresstabellen (Symboltabellen) realisieren, sollte man sich von dieser Vorstellung lösen, und C++-Referenzen als transparente Objektnamen betrachten sowie C-Zeigerwerte als tatsächliche Speicheradressen von Objekten, denn das sind sie wirklich, ohne einen Vergleich mit den Hash-Werten der Java-Referenzen zu ziehen.
Zeiger

Die Semantik ist unscharf formuliert: meint manchmal eine Zeigervariable, manchmal aber auch nur einen Zeigerwert
Zeigerwert

der Wert einer Zeigervariablen, d.h. die Speicheradresse eines Objektes. Damit hat der Zeigerwert den Datentyp: Speicheradresse eines Objekte des Typs <typ>
Zeigervariable

Variable, die nur Adresswerte des zugehörigen Typs (Speicheradresse eines Objektes des Typs <typ>) speichern kann
Zielobjekt

das Objekt, auf das der Zeiger verweist, d.h. das Objekt, dass sich an der Speicheradresse (dem Zeigerwert) der Zeigervariablen befindet.
Rohe Zeiger (raw pointer) vs intelligente Zeiger (smart pointer)
Das Konzept des Zeigers (rohe Zeiger) ist elementar in C++. Leider aber auch die Quelle vieler Programmierfehler. Diese Kapitel bespricht daher nur die unumgänglichen Einsatzgebiete von rohen Zeigern und geht dann über zu den sog. intelligenten Zeigern.

Initialisierung von Zeigervariablen
Wie bei allen Variablendefintionen gewöhnen wir uns auch bei Zeigervariablen an, diese in der Definitionsanweisung zu initialisieren: entweder mit einem gültigen Adresswert eines schon bestehenden Objektes oder mit dem ungültigen Zeigerwert nullptr (s.a. nullptr).

Dabei tauchen (wieder einmal) die Symbole * und & auf mit folgenden Bedeutungen:

abgeleiteter Typ Zeiger auf Objekt

In <type>* <name> = nullptr; wird die Zeigervariable <name> mit dem Typ <type>*, d.h. Zeiger auf ein <type>-Objekt definiert und mit dem Wert nullptr initialisiert.
nullptr

spezieller (polymorpher) Zeigerwert mit der Bedeutung: Zeiger auf nichts.
Indirektionsoperator (Dereferenzierungsoperator)

in der Schreibweise *<name> bedeutet * den Indirektionsoperator (Dereferenzierungsoperator), der das Zielobjekt selbst bestimmt. Bildlich gesprochen: man folgt dem Zeiger bis zum Zielobjekt. Der Name Dereferenzierungsoperator ist missverständlich! Der Typ dieses Ausdrucks ist der Basistyp von <name>.
Adressoperator

in der Schreibweise &<objectname> bedeutet & den Adressoperator, der die Speicheradresse des Objektes <objectname> bestimmt. Der Typ dieses Ausdrucks ist Zeiger auf Objekttyp.
Notationen: Definition von Zeigervariablen

Die folgenden Notationsvarianten für Definitionsanweisungen von Zeigervariablen sind möglich (s.a. Deklaration von Referenzen):

int*  ptr1 = nullptr; (1)
int * ptr2 = nullptr;
int  *ptr3 = nullptr;
1 Empfohlene Variante

Das Symbol * hat viele Semantiken (bspw. auch als Indirektionsoperator). Um Verwechslungen auszuschließen, sollte die Variante int* verwendet werden: dies kann man dann (von rechts nach links) als Zeiger für ein int-Objekt lesen.
Einsatz von Zeigern
Einer Zeigervariablen können (neue) Werte zugewiesen werden. Damit kann eine Zeigervariable nacheinander auf unterschiedliche Objekte zeigen. Dies ist oft nützlich für Iterationen. Eine Zeigervariable ist die simpelste Form eines Iterators in C++.

In einem Block Zeigervariable für lokale Variable zu definieren (s.o.), diente nur der prinzipiellen Darstellung. Sinnvollere Einsatzzwecke sind Parameterübergabe und Ergebnisrückgabe bei Funktionen.

2.2. Zeiger-Werte als Parameter (call-by-value)

Das folgende Bild verdeutlicht die Mechanik bei einem Zeiger als Funktionsparameter:

Bild 2. Parameterübergabe call-by-value mit Zeiger

Werden Zeigerwerte per-value in einen Funktionsparameter kopiert, so zeigt dieser Funktionsparameter auch auf dasselbe Zielobjekt. Damit kann man (zunächst) uneingeschränkt auf das Zielobjekt als Input/Output-Parameter zugreifen:

Quelltext 2. Zeilen aus der Datei ppc0603.cc 
1#include <iostream>
2void foo(int* const inOutPtr) { (1)
3    *inOutPtr += 1;
4}
5int main() {
6    int a = 42;
7    foo(&a); (2)
8    std::cout << "Der Wert von a = " << a << std::endl;
9}
1 Das Zielobjekt ist ein Input/Output-Parameter
2 Der Adressoperator bestimmt die Adresse von a, die als Wert in den Funktionsparameter von foo() kopiert wird
Ausgabe 2. Ausgabe des Programms: ppc0603
Der Wert von a = 43

Soll das Zielobjekt ausschließlich als Input-Parameter verwendet werden, so muss das Zielobjekt als const qualifiziert werden.

2.3. Zeiger und const

Ein Zeiger besteht aus einem Zeigerwert, d.h der Speicheradresse des Zielobjektes und einer Zeigervariablen. Es sind daher zwei Objekte (Zeigervariable und Zielobjekt) beteiligt, die jeweils const qualifiziert werden können.
<type>* <variable>

<variable> ist eine nicht-konstante Zeigervariable auf ein nicht-konstantes Zielobjekt
const <type>* <variable>

<variable> ist eine nicht-konstante Zeigervariable auf ein konstantes Zielobjekt
<type>* const <variable>

<variable> ist eine konstante Zeigervariable auf ein nicht-konstantes Zielobjekt
const <type>* const <variable>

<variable> ist eine konstante Zeigervariable auf ein konstantes Zielobjekt

Im folgenden Quelltext ist des Zielobjekt const (Input-Parameter):

Quelltext 3. Zeilen aus der Datei ppc0604.cc 
 1#include <iostream>
 2void foo(const int* const inPtr) { (1)
 3    *inPtr += 1; (2)
 4    int value = *inPtr; (3)
 5}
 6int main() {
 7    int a{42};
 8    foo(&a); (4)
 9    std::cout << "Der Wert von a = " << a << std::endl;
10}
1 Das Zielobjekt ist ein Input-Parameter
2 Ergibt einen Compiler-Fehler, denn das Zielobjekt von inPtr ist const
3 Sinnvoll und möglich
4 Der Adressoperator bestimmt die Adresse von a, die als Wert in den Funktionsparameter von foo() kopiert wird

Eine Modifikation oder Zuweisung ist daher nicht möglich:

2.5. nullptr:der Zeiger auf das Nichts

Der Begriff roher Zeiger rührt aus der Tatsache her, dass einer Zeigervariable zunächst einmal ungeprüft jeder Adresswert zugewiesen werden kann: dies kann zu Situationen führen, dass an der Adresse sich gar kein Objekt des Zeigerzieltyps befindet. Dies tritt regelmäßig bei der Verwendung von uninitialisierten Zeigervariablen auf.

Eine andere Fehlerquelle ist die Verwendung eines initialisierten, aber ungültigen Zeigerwertes. Für die Initialisierung einer Zeigervariable mit einem definitiv ungültigen Zeigerwert steht das Zeigerliteral nullptr zur Verfügung. Zudem kann jede Zeigervariable auch mit dem Literal 0 initialisiert werden.

Quelltext 5. Zeilen aus der Datei ppc0607.cc 
 1#include <iostream>
 2#include "point50.h"
 3void foo(const Point* const point) {
 4    const DRect rect{point->svgArea()}; (1)
 5    std::cout << rect.area() << std::endl;
 6}
 7int main() {
 8    Point p;
 9    foo(&p);
10    foo(nullptr); (2)
11    std::cout << "Diese Ausgabe wird nicht mehr erfolgen!" << std::endl;
12}
1 Zugriff über einen nullptr führt zu einem Programmabbruch
2 Dies ist an dieser Stelle gleichbedeutend mit foo(0)
Ausgabe 5. Ausgabe des Programms: ppc0607
400
Checked-Pointer Idiom

Der Programmabbruch beim Zugriff über einen Null-Zeigerwert (nullptr oder 0) ist wichtig bei der Aufdeckung von Fehlern. Auf der anderen Seite besitzen die Zeigertypen damit als einziger primitiver Datentyp in ihrem Wertebereich (Speicheradressen) einen definitiv ungültigen Wert. Damit läßt sich der Null-Zeigerwert als Sentinel bspw. bei der Realisierung von verketteten Datenstrukturen (verkettete Liste) einsetzen.

Die Prüfung kann als Auswahlanweisung if (ptr != nullptr) {…​} explizit oder auch durch die implizite Typwandlung von Zeigerwerten nach bool als if (ptr) {…​} prägnant geschrieben werden.

Einsatz des Checked-Pointer-Idiom, wenn der Aufruf der Funktion mit einem Null-Zeiger zum Regelfall zählt ( sollte das nicht der Regelfall sein, ist ist eine Zusicherung die richtige Lösung):

Quelltext 6. Zeilen aus der Datei ppc0608.cc 
 1#include <iostream>
 2#include "point50.h"
 3void foo(const Point* const point) {
 4    if (point) { (1)
 5        const DRect rect{point->svgArea()};
 6        std::cout << rect.area() << std::endl;
 7    }
 8}
 9int main() {
10    Point p;
11    foo(&p);
12    foo(nullptr); (2)
13    std::cout << "Diese Ausgabe erfolgt nun trotz nullptr!" << std::endl;
14}
1 Bei der Verwendung von rohen Zeigern ist die Gültigkeit des Zeigerwertes vor der Benutzung zu prüfen
2 Dies ist an dieser Stelle gleichbedeutend mit foo(0)
Ausgabe 6. Ausgabe des Programms: ppc0608
400
Diese Ausgabe erfolgt nun trotz nullptr!

2.6. Zeiger und Zusicherungen

Zählt der Null-Zeiger nicht zum validen Wertebereich eines Zeigerparameters, so muss die Gültigkeit auf jeden Fall durch eine Zusicherung (Vorbedingung, Assertion) sichergestellt werden. Sollte die Vorbedingung dann verletzt sein, so erfolgt durch die assert-Anweisung ein Programmabbruch mit aussagekräftiger Fehlermeldung.

Quelltext 7. Zeilen aus der Datei ppc0609.cc 
 1#include <iostream>
 2#include <cassert>
 3#include "point50.h"
 4void foo(const Point* const point) {
 5    assert(point); (1)
 6    const DRect rect{point->svgArea()};
 7    std::cout << rect.area() << std::endl;
 8}
 9int main() {
10    Point* p{nullptr}; (2)
11    foo(p); (3)
12}
1 Prüfen der Vorbedingung
2 Initialisierung der Zeigervariable
3 Hier ist die Vorbedingung von foo() nicht erfüllt → Programmabbruch

3. Details

3.1. Strings: std::string, Zeiger und C-Strings

C-Strings
C-String-Literale wie etwa "zeichenkette" sind nicht vom Typ std::string, sondern sie evaluieren zu einem Wert des Typs const char*, d.h. Zeiger auf ein konstantes Objekt vom Typ char. Von diesem char-Objekt wird dann angenommen, dass es sich dabei um das erste Zeichen einer zusammenhängenden Folge (rohes Array) von char-Objekten handelt. Das letzte Element dieser Folge muss '\0' sein.

Die Längenbestimmung eines C-Strings geschieht hierbei implizit durch die Position des Wächterelements '\0' als letztes Zeichen in der Folge.

An raw array in C++ is a data type that is so stupid that it didn’t even know how many elements it got.
— B. Stroustrup
GoingNative 2013

Aus dieser Beschreibung sollte wie selbstverständlich hervorgehen, dass in C++ die Verwendung von C-Strings auf das absolut notwendige Mindestmaß beschränkt werden soll. Die Manipulationsfunktionen (wie strncpy) sind zu vermeiden.

Durch implizite Typumwandlungen von C-String nach std::string beschränkt sich der Einsatz auch nur auf C-String-Literale.
Quelltext 8. Zeilen aus der Datei ppc0610.cc [Snippet: A] (einige Zeilen nicht dargestellt)

 2public:
 3    A(const std::string&) {
 4    }
 5};
 6int main() {
 7    std::string s = "abc"; (1)
 8    A a1{"abc"}; (2)
 9//    A a2 = "abc"; (3)
10// ...
11}
1 Hier kommt der Typumwandlungskonstruktor std::string(const char*) zum Einsatz.
2 Auch hier findet eine implizite Typumwandlung von const char* nach std::string statt.
3 Nicht möglich, weil nur einstufige, implizite Typwandlungen ausgeführt werden;
Quelltext 9. Zeilen aus der Datei ppc0610.cc [Snippet: udl] (einige Zeilen nicht dargestellt)

3.2. Kopierkonstruktor

Bei der Kopierkonstruktion (Kopierinitialisierung) etwa für den Typ Point in der Art

Point p1;
Point p2 = p1; // Kopierkonstruktion

erwarten wir, dass alle nicht-statischen Datenelemente des Quellobjektes in das Zielobjekt kopiert werden. Das ist auch in der Tat so. Dieses Verhalten kann aber in bestimmten Fällen unerwünscht sein.

Wir erweitern die Klasse Point um eine unikate, konstante Seriennummer. Diese soll einfach ein fortlaufende Nummer sein:

Quelltext 10. Zeilen aus der Datei point51.h [Snippet: Point] (einige Zeilen nicht dargestellt)
1class Point {
2// ...
3    const int mSNR; (1)
4    inline static int mSVGRadius{10};
5    inline static int mObjectCounter{0}; (2)
6};
1 Keine in-class-Initialisierer, damit man die Generierung im Konstruktor nicht vergisst.
2 Diese Klassenvariable zählt die bisher erzeugten Instanzen

In der Initialisierungsliste der Konstruktoren wird aus der Objektanzahl die Seriennummer gebildet:

Quelltext 11. Zeilen aus der Datei point51.cc [Snippet: ctor]

3.3. Konstruktor-Delegation

Bei der obigen Realisierung der Konstruktoren fällt auf, dass bspw. die Generierung der Seriennummer in allen Konstruktoren auftaucht. Dies verursacht Code-Duplizierungen.

Hier ist es sinnvoll, einen Konstruktor (wieder) einzuführen, der mit den unspezifischen Datentypen double und std::string arbeitet: diesen dann aber private zu deklarieren. Denn der Grundsatz des Klassendesigns ist es, die Klasse effektiv, einfach und sicher verwenden zu können. Dies bedeutet nicht, dass es der Author der Klasse besonders einfach haben soll.
Eine Klasse sollte leicht richtig und schwer falsch zu benutzen sein.
— Scott Meyers

Dieser soll alle Datenelemente der Klasse ebenfalls kopier-zuweisen, was allerdings bei const-Datenelementen nicht möglich ist (s.a. obige Fehlermeldung).

Deswegen wird ein eigener Kopierzuweisungsoperator deklariert

Der Zeiger this auf das eigene Objekt
In C++ ist this ein Zeiger auf das eigene Objekt. Das eigene Objekt selbst ist daher mit dem Indirektionsoperator auf this angewendet erreichbar.

Wichtig bei der Realisierung des Kopierzuweisungsoperators ist, dass das Ergebnis des Operators das eigene Objekt ist. Das bedeutet eine Rückgabe per non-const-Referenz für *this. Dies ist wichtig für die Gleichstellung zu den primitiven Datentypen und den Kettenzuweisungen:

int a = 0;
int b = 1;
int c = 2;

a = b = c; // Kettenzuweisung

Point p1{XCoor{1.0}, YCoor{2.0}};
Point p2{XCoor{2.0}, YCoor{3.0}};
Point p3{XCoor{3.0}, YCoor{4.0}};

p1 = p2 = p3; // Kettenzuweisung
Schematisierter Kopierzuweisungsoperator
Die obige Realisierung des Kopierzuweisungsoperators kann universell eingesetzt werden, sofern es wiederum nur Kopierzuweisungen von primitiven DT oder ausnahmesichere Kopierzuweisungen von UDT sind. Meistens ist jedoch ein anderer, schematisierter Aufbau besser geeignet (Copy-Swap-Idiom).

3.5. Verkettung von Mutatoren

Bei der Verkettung des Kopierzuweisungsoperators haben wir gesehen, dass hier das eigene Objekt als non-const-Referenz zurückgegeben wird.

Dasselbe Idiom lässt sich bei den Mutatoren (aka setter) anwenden:

4. Rückblick

Bislang war es so, dass die Methode SVGFile::add(const Point& point) spezifisches Wissen über die Klasse Point haben musste, um die Ausdehung in der SVG-Zeichenfläche zu ermitteln. Stattdessen sollte die Klasse Point diese Information zur Verfügung stellen.

Wir modellieren die Ausdehung als ein diskretes Rechteck (DRect), dass durch seine zwei gegenüberliegenden Eckpunkte upperLeft und bottomRight vom Typ DPoint (diskreter Punkt) gebildet wird.

Die Klasse DPoint ist ein simpler POD-Typ:

Quelltext 24. Zeilen aus der Datei point50.h [Snippet: DPoint] (einige Zeilen nicht dargestellt)
1class DPoint { (1)
2public:
3    int mX {0};
4    int mY{0};

1 Die Klasse ist wieder ein POD

Die Klasse DRect hat als Besonderheit den Typumwandlungsoperator explicit operator bool() const sowie den Additionszuweisungsoperator +=. Der Typumwandlungsoperator nach bool ist nicht wirklich erforderlich und hier nur als ein Beispiel anzusehen: ein gültiges DRect-Objekt besitzt eine Fläche > 0.

Der Additionszuweisungsoperator += bildet das umschreibende Rechteck.
