2. Abstraktion der Klasse Point

In einem Grafikprogramm gibt es nicht nur Punkte zu zeichnen, sondern weitere Grafikobjekte wie eine Linie, ein Rechteck, eine Ellipse oder auch einen Kreis und ein Quadrat. Alle diese Objekte sollen durch die Klasse SVGFile korrekt in eine SVG-Datei eingefügt werden.

Aus (jetziger) Sicht der Klasse SVGFile lassen sich die gemeinsamen Anforderungen an ein Grafikobjekt knapp zusammenfassen:

  • Das Grafikobjekt muss eine Darstellung als XML-Element im SVG-Format liefern können.

  • Das Grafikobjekt muss seine Ausdehnung in der SVG-Zeichenebene liefern können.

Beides sind Verhaltensanforderungen und damit Anforderungen an eine gemeinsame Schnittstelle. Dies wird in C++ wie auch in Java durch das Schnittstellenkonzept ausgedrückt. Man kann sich auch sofort eine konkrete Klasse Line vorstellen, die ebenfalls diese Schnittstelle erfüllt.

Bild 1. Erweitertes Klassendiagramm: Die konkrete Klasse Point und Line sowie die Schnittstelle SVGShape und die Klasse SVGFile

In dem obigen UML Klassendiagramm haben wir die Schnittstelle SVGShape, die von den konkreten Klasse Point und Line realisiert werden. Damit die die Klasse SVGFile in der Lage, statt den konkreten Klassen nur noch die Schnittstelle SVGShape zu verwenden.

3. Eine Schnittstellendeklaration in C++

In Java existiert hierfür das Schlüsselwort interface. In C++ wird dies durch eine Klasse mit rein-virtuellen Elementfunktionen realisiert (s.a. abstrakte Klasse und virtuelle Elementfunktion) .

 2#if __has_include("../ppc.h")
 3# include "../ppc.h"
 4#endif
 5#include <string>
 6#include "dgeometry.h"
 7class SVGShape { (1)
 8public:
 9    virtual std::string toSVG() const = 0; (2)
10    virtual DRect svgArea() const = 0; (3)
11    virtual ~SVGShape(); (4)
12};
1 Diese Klasse enthält nur rein-virtuelle Elementfunktionen und stellt damit eine Schnittstelle dar.
2 Die Qualifizierungen virtual und = 0 deklarieren diese Elementfunktion als rein-virtuell.
3 Diese Elementfunktion ist ebenfalls rein-virtuell.
4 Der Destruktor muss hier virtuell deklariert werden.

Die Datei svgshape.cc enthält nur die Definition des virtuellen Destruktors (s.a. Notwendigkeit des virtuellen Destruktors):

1 Das Schlüsselwort virtual darf nur in der Deklaration angegeben werden. Es gehört nicht zur Signatur.

Schnittstellen in C++

In Java gibt es das interface-Konstrukt. In C++ müssen die folgenden Punkte beachtet werden:

  • Schnittstellen werden in C++ durch abstrakte Klassen (s.a. abstrakte Klasse) dargestellt, die ggf. ausschließlich statische Datenelemente enthalten.

  • Eine Klasse ist dann abstrakt, wenn sie nicht instanziierbar ist.

  • Ein Klasse ist dann nicht instanziierbar, wenn sie unvollständig ist. Dies erreicht man mit rein-virtuellen Elementfunktionen.

  • Eine rein-virtuelle Elementfunktion wird als virtual deklariert und mit = 0 qualifiziert.

  • Das Schlüsselwort virtual kennzeichnet ein Elementfunktion als dynamisch gebunden, d.h. für die Laufzeitpolymorphie (s.a. virtuelle Elementfunktion).

4. Vererbungsbeziehung

Deklaration einer Vererbungsbeziehung

Die Schlüsselwörter public und private (auch protected) (s.a. Zugriffspezifizierer) können zur Deklaration einer Vererbungsbeziehung (s.a. abgeleitete Klasse) verwendet werden:

public

Ergibt eine Schnittstellenvererbung und es gilt das Liskov’sche Substitutionsprinzip: der abgeleitete Typ kann immer an die Stelle des Basistyps treten.
private

Ergibt eine Implementierungsvererbung ohne Substitutionsprinzip: der abgeleitete Typ erbt nicht die öffentliche Schnittstelle des Basistyps. Er kann aber die (mindestens) protected Elementfunktionen (Implementierung) des Basistyps verwenden.

5.1. Statischer und dynamischer Typ

Betrachten wir zunächst den folgenden Codeabschnitt:

Quelltext 13. Zeilen aus der Datei ppc0920.cc [Snippet: mainref] 
1int main() {
2    Derived derived; (1)
3    Base base; (2)
4    Base& base2 = derived; (3)
5    base2.nonvirtualfunction();
6    base2.virtualfunction();
7// ...
8}
1 Ein Derived-Objekt wird in der Variable derived instanziiert.
2 Eine Variable des Typs Base wird definiert, damit wird ein Objekt dieses Typs erzeugt.
3 Hier wird base2 als ein weiterer Name für das Objekt der Variable derived deklariert.

Die Situation im Speicher verdeutlicht auch das folgende Bild:

Bild 5. Die zwei Objekte des Typs Derived bzw. Base im Speicher und ihre Namen (Referenzen)

  • Der Name base (statischer Typ: Base) bezeichnet ein Objekt des Typs Base.

  • Der Name derived (statischer Typ: Derived) bezeichnet ein Objekt des Typs Derived. Das beinhaltet ein anonymes Basisklassenobjekt vom Typ Base.

  • Der Name base2 (statischer Typ: Base) bezeichnet dasselbe Objekt wie der Name derived; das ist vom dynamischen Typ Derived.

Statischer Typ

ist der Typ der Referenz, und bestimmt die verwendbare Schnittstelle.
Dynamischer Typ

ist der Typ des Objektes, das mit der Referenz bezeichnet wird. Bei virtuellen Elementfunktionen bestimmt der dynamische Typ die Auswahl der Elementfunktion.

Damit sind über die Referenz base2 nur die Elemente der öffentlichen Schnittstelle Base erreichbar, das Datenelement mDerived kann also mit base2 nicht angesprochen werden.

Bei überschriebenen virtuellen Elementfunktionen wird dann allerdings die Realisierung gemäß dem dynamischen Typ gewählt. Dies ist das Java-Verhalten.

Bei überschriebenen nicht-virtuellen Elementfunktionen bestimmt der statische Typ der Referenz die Funktionsauswahl. Daher sollte man nicht-virtuelle Elementfunktionen nicht überschreiben (das Schlüsselwort override ist auch nicht anwendbar)!

Polymorphe Verwendung von Objekten

Die folgenden Regeln bestimmen die polymorphe Verwendung von Objekten:

  • Eine polymorphe Elementfunktionsauswahl (Auswahl anhand des Objekttyps) kann nur bei einem Zugriff über eine Basisklassen-Referenz oder einen Basisklassen-Zeiger erfolgen.

  • Nur virtuelle Elementfunktionen nehmen an der polymorphen Auswahl teil.

Um Probleme (s.a. Slicing) zu vermeiden, sollte man nach der Regel verfahren:

  • Wertsemantik (kopierbare Datentypen) und Klassenhierarchien passen nicht zusammen.

5.2. Eingebettetes Basisklassenobjekt und das sog. objectslicing

Eine ganz andere Situation ergibt sich in dem folgenden Codabschnitt:

Quelltext 15. Zeilen aus der Datei ppc0920.cc [Snippet: mainslice] 
1int main() {
2// ...
3    base = derived; (1)
4// ...
5}
1 Dem Objekt der Variablen base soll das Objekt der Variablen derived kopier-zugewiesen werden! Achtung: Hier passiert das sog. slicing: nur der Base-Anteil von derived wird zugewiesen!

Wie im obigen Bild bzw. in Bild schon angedeutet, verschachteln sich Objekte und (anonyme) eingebettete Basisklassen-Objekte wie Matrjoschkas ineinander.

Bild 8. Das eingebettete Basisklassenobjekt des Typs Base in einem Objekt des Typs Derived

Bei einer Kopierzuweisung eines abgeleiteten Typs an ein Objekt des Basistyp oder auch bei einer Kopierkonstruktion eines Basistyps von einem abgeleiteten Typs aus, kann nur der Anteil des anonymen, eingebetteten Basisklassenobjekts in das Zielobjekt kopiert werden.
Bild 9. Der Effekt des Objektslicing: nur der Base-Anteil (eingebettetes Basisklassenobjekt) wird kopierzugewiesen.

Dies findet natürlich auch bei Funktionsaufrufen statt:

Quelltext 16. Zeilen aus der Datei ppc0920.cc [Snippet: mainparam] 
1int main() {
2// ...
3    foo(derived); (1)
4    bar(derived); (2)
5// ...
6}
1 Bei Parameterübergabe per-value kommt es auch zu einem Slicing, denn hier findet eine Kopierkonstruktion in die Parametervalue statt.
2 Die Parameterübergabe per-reference vermeidet das Slicing.
Quelltext 17. Zeilen aus der Datei ppc0920.cc [Snippet: functions] 
 1void foo(Base x) { (1)
 2    x.mBase;
 3//    x.mDerived; (2)
 4    x.nonvirtualfunction();
 5    x.virtualfunction();
 6}
 7void bar(const Base& x) { (3)
 8    x.mBase;
 9//    x.mDerived; (4)
10    x.nonvirtualfunction();
11    x.virtualfunction();
12}

2 Wegen Slicing nicht vorhandenes Datenelement.
3 Parameterübernahme per-reference vermeidet Slicing, denn x ist hier nur ein weiterer Name (statischer Typ: Base) für das Objekt des Aufrufers
4 Über den statischen Type nicht erreichbares Datenelement

6. Löschen von Freispeicherobjekten über Basisklassen-Zeigern

Die folgende Regel ist zu beachten:

So wichtig für die Programmfunktion die korrekte polymorphe Auswahl von allgemeinen Elementfunktionen ist, so lebenswichtig ist die korrekte Auswahl des Destruktors des Objektes über einen Basisklassen-Zeiger. Aus diesem Grunde muss⁠[1] in einer Klassenhierarchie der Destruktor ebenfalls eine virtuelle Elementfunktion sein.

Wir verdeutlichen das an dem Beispiel der Klasse PointList aus der Lerneinheit 08. Dazu schreiben wir eine Schnittstelle List, die dann von der Klasse PointList zu realisieren ist.
