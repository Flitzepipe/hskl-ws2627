2. Eine Klasse Point

2.1. Überladen von Elementfunktionen

Für die folgende Verwendung der Klasse Point braucht man einen Standardkonstruktor und einen allgemeinen Konstruktor. Die letzte Version realisierte dies durch Überladung des Konstruktors. Für das folgende Beispiel würde man eine dritte überladene Variante des Konstruktors benötigen:

Quelltext 1. Zeilen aus der Datei ppc0200.cc [Snippet: ctor] 
1Point p1; (1)
2Point p2{1.0}; (2)
3Point p3{1.0, 2.0}; (3)
1 nicht-primitiver Datentyp → default-initialization → Standardkonstruktor
2 allgemeiner Konstruktor
3 allgemeiner Konstruktor

2.2. Vorgabewete in Parameterlisten

Eine andere Möglichkeit, denselben Effekt zu erreichen, ist der Einsatz von Vorgabewerten (default-values) für die Funktionsparameter:

Quelltext 2. Zeilen aus der Datei point10.h [Snippet: ctor] 
1Point(double x = 0.0, double y = 0.0);
Vorgabewerte für Funktionsparameter und Funktionsüberladung
Im obigen Beispiel ist der Algorithmus des Konstruktors bei einer unterschiedlichen Parameterliste, die nur aus double-Werten besteht, immer derselbe: die Datenelemente des Objektes werden mit den übergebenen Werten initialisiert; für die fehlenden wird lediglich der Wert 0.0 eingesetzt. Daher ist es sinnvoll, hier Vorgabewerte einzusetzen. Sollte sich der Algorithmus für eine andere Parameterzusammensetzung unterscheiden, so muss die Funktion überladen werden. Gerade bei Konstruktoren (derselbe Algorithmus) wird deswegen häufig mit Vorgabewerten gearbeitet.

Es müssen nicht für alle Parameter Vorgabewerte eingesetzt werden.

foo(int x, int y = 0);

kann mit einem oder zwei int-Werten aufgerufen werden:

foo(0);
foo(0, 1);

Ist jedoch für einen Parameter ein Vorgabewert eingesetzt, so müssen auch alle folgenden Parameter Vorgabewerte bekommen, damit die Eindeutigkeit der Zuordnung gewahrt bleibt:

bar(int x, int y = 0, int z); (1)
1 nicht möglich

Damit haben wir die folgende Klassenschnittstelle:

Quelltext 3. Zeilen aus der Datei point10.h [Snippet: Point] 
1class Point {
2public:
3    Point(double x = 0.0, double y = 0.0);
4// ...
5private:
6// ...
7};

Ob alles wie gewünscht funktioniert, testen wir:

Quelltext 4. Zeilen aus der Datei ppc0200.cc [Snippet: test] 
1assert(p1.getX() == 0.0); (1)
2assert(p1.getY() == 0.0);
3assert(p2.getX() == 1.0);
4assert(p2.getY() == 0.0);
5assert(p3.getX() == 1.0);
6assert(p3.getY() == 2.0);
1 Achtung: Ein direkter Vergleich von Fließkommawerten ist immer falsch!
Ein direkter Vergleich von Fleißkommawerten (double, float) ist immer falsch. Stattdessen sollte ein relatives Differenzenverfahren angewendet werden.
Wir haben im obigen Beispiel Zusicherungen (Assertionen) in der Funktion main() benutzt, um sicherzustellen, dass die Klasse Point dem vorgegebenen Verhalten entspricht. Fehlschlagende Assertionen lassen das Programm abbrechen. Damit sind allerdings die Tests vom eigentlich Testobjekt (der Klasse Point) strukturell getrennt. Dies ist nicht sinnvoll. Dazu erfahren wir später mehr.

Um das Vergleichen von Fließkommawerten zu ermöglichen, erstellen wir eine Klasse Math mit einer statischen Elementfunktion (Klassenmethode) bool equal(double a, double b):

Quelltext 5. Zeilen aus der Datei math.h [Snippet: mathequal] 
1class Math {
2public:
3    static bool equal(double a, double b);
4// ...
5};

Und die Definition:

Quelltext 6. Zeilen aus der Datei math.cc [Snippet: mathequal] 
1bool Math::equal(const double a, const double b) {
2    const double epsilon{1e-10};
3    const double difference{a - b};
4    if ((difference > -epsilon) && (difference < epsilon)) {
5        return true;
6    }
7    return false;
8}

Da unsere Klasse Math bislang keine Datenelemente enthält, hätte man die Funktion bool equal(double a, double b) auch als freie Funktion schreiben können.

Wir verbessern unsere Tests:

Quelltext 7. Zeilen aus der Datei ppc0201.cc [Snippet: test] 
1assert(Math::equal(p1.getX(), 0.0));
2assert(Math::equal(p1.getY(), 0.0));
3assert(Math::equal(p2.getX(), 1.0));
4assert(Math::equal(p2.getY(), 2.0));

2.3. Testen

Der Code zum Testen einer Klasse, d.h. die Testfälle sollten nicht strukturell von der zu testenden Klasse getrennt sein. Deswegen schreiben wir die Testfälle ab jetzt in die Implementierungsdatei der Klasse. Ohne ein komplexes Testrahmenwerk (etwa boost-test oder google-test) einzusetzen, verwenden wir eine simple, aber für einfache Anwendungen ausreichende Testklasse SimpleTestCase aus der Headerdatei bzw. Implementierungsdatei.

Damit ist es möglich, die Testfälle

  • in die Implementierungsdatei der Klasse zu schreiben, die getestet werden soll

  • beim Start eines Programms, dass diese Klasse verwendet, automatisch ablaufen zu lassen.

Quelltext 8. Zeilen aus der Datei point11.cc [Snippet: test] 
 1#include "../lib/simpletest.h" (1)
 2SIMPLETEST("Point 1") { (2)
 3    Point p;
 4    if (!Math::equal(p.getX(), 0.0)) return false;
 5    if (!Math::equal(p.getY(), 0.0)) return false;
 6    return true;
 7};
 8SIMPLETEST("Point 2") { (3)
 9    Point p{1.0, 2.0};
10    if (!Math::equal(p.getX(), 1.0)) return false;
11    if (!Math::equal(p.getY(), 2.0)) return false;
12    return true;
13};
1 Inklusion der Header-Datei für SIMPLETEST
2 Definition eines ersten Testfalls
3 Definition eines zweiten Testfalls

Die Verwendung der Klasse SimpleTestCase ist durch ein Präprozessormakro recht einfach:

SIMPLETEST("Testfallname") {
	if (!expected) return false;
	return true;
};

In dem Klammerpaar {} ist der testende Code, der false für einen fehlgeschlagenen Testfall zurück liefert. Dies wird dann in einer entsprechenden Ausgabe protokolliert.

Ausgabe 1. Ausgabe des Programms: ppc0201
Test(Point 1,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point11.cc,41) ok (1/0)
Test(Point 2,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point11.cc,50) ok (2/0)

Sollte ein Fehler auftreten (im folgenden Beispiel durch einen fehlerhaften Testfall provoziert), so erhält man eine entsprechende Ausgabe:

Quelltext 9. Zeilen aus der Datei point12.cc [Snippet: test] 
1#include "../lib/simpletest.h"
2SIMPLETEST("Point 3") {
3    Point p{1.0};
4    if (!Math::equal(p.getX(), 1.0)) return false;
5    if (!Math::equal(p.getY(), 0.1)) return false; (1)
6    return true;
7};
1 nur zu Demonstrationszwecken

Es ergibt sich die Ausgabe dazu:

Ausgabe 2. Ausgabe des Programms: ppc0202
Test(Point 1,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point12.cc,40) ok (1/0)
Test(Point 2,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point12.cc,49) ok (2/0)

3. Details

3.1. Weitere Elementfunktionen

Beobacher und Mutatoren
Die bisherigen Elementfunktionen double getX() const und double getY() const waren sog. Beobachter-Funktionen (getter). Der const-Qualifizierer nach dem Elementfunktionsnamen war dafür entscheidend, dass diese Funktionen den Objektzustand nicht ändern können. Elementfunktion ohne den const-Zusatz können den Objektzustand modifizieren und heißen deswegen Mutatoren (setter).

Beispiele für Mutatoren:

Quelltext 10. Zeilen aus der Datei point13.h [Snippet: Pointsetter] 
1class Point {
2public:
3// ...
4    void setX(double x);
5    void setY(double y);
6    void move(double dx, double dy);
7private:
8// ...
9};

Die Tests für die Mutatoren:

Quelltext 11. Zeilen aus der Datei point13.cc [Snippet: testsetter] 
 1SIMPLETEST("Point setX") {
 2    Point p;
 3    p.setX(1.0);
 4    if (!Math::equal(p.getX(), 1.0)) return false;
 5    if (!Math::equal(p.getY(), 0.0)) return false;
 6    return true;
 7};
 8SIMPLETEST("Point setY") {
 9    Point p;
10    p.setY(1.0);
11    if (!Math::equal(p.getX(), 0.0)) return false;
12    if (!Math::equal(p.getY(), 1.0)) return false;
13    return true;
14};
15SIMPLETEST("Point move") {
16    Point p;
17    p.move(1.1, 2.2);
18    if (!Math::equal(p.getX(), 1.1)) return false;
19    if (!Math::equal(p.getY(), 2.2)) return false;
20    return true;
21};

3.2. Die Klasse std::string für Zeichenketten

Die Kernsprache C++ hat für Zeichenketten (string) nur eine sehr rudimentäre Unterstützung aus der Sprache C genannt C-String (dazu erfahren wir später mehr). Wesentlich komfortabler geht es mit der Klasse std::string der C++-Standardbibliothek.

Zeichenkettenliterale wie "abc" werden in C++ als C-Strings (s.a. LE-06 Strings) dargestellt. Diese sind aber durch eine implizite Typkonversion in den Typ std::string konvertierbar,

Wir fügen der Klasse Point noch ein Farbattribut hinzu:

Quelltext 12. Zeilen aus der Datei point14.h [Snippet: PointColor] 
 1class Point {
 2public:
 3// ...
 4    std::string getColor() const;
 5// ...
 6    void setColor(std::string color);
 7private:
 8// ...
 9    std::string mColor; (1)
10};
1 Standardkonstruktor → leerer String in mColor
Quelltext 13. Zeilen aus der Datei point14.cc [Snippet: testsetter] 
1SIMPLETEST("Point color") {
2    Point p;
3    if (p.getColor() != "black") return false; (1)
4    return true;
5};
1 Hier findet eine implizite Typwandlung des C-Strings "black" in den Typ std::string statt.
Ausgabe 3. Ausgabe des Programms: ppc0204
Test(Point ctor1,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point14.cc,68) ok (1/0)
Test(Point ctor2,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point14.cc,77) ok (2/0)
Test(Point ctor3,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point14.cc,86) ok (3/0)
Test(Point setX,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point14.cc,95) ok (4/0)
Test(Point setY,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point14.cc,105) ok (5/0)
Test(Point move,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point14.cc,115) ok (6/0)
Test(Point color,/home/lmeier/Lehre/osscourse-git/pcpp/src/ppc02/point14.cc,125) failed (7/1)

Auch hier schlägt der Testfall Point color erst einmal fehl: schließlich wurde das Farbattribut mColor nicht initialisiert. Interessant ist aber, dass wir von

Quelltext 14. Zeilen aus der Datei ppc0204.cc [Snippet: getColor] 
1Point p1;
2std::cout << p1.getColor() << std::endl;

nur eine Leerzeile als Ausgabe und keine zufällige Zeichenkette erhalten.

Eine Definition ohne Initialisierer bedeutet eine Standardinitialisierung: dies ist bei primitiven DT → nix tun, aber bei nicht-primitiven DT (UDT) → Standardkonstruktor. Im Falle von std::string ergibt die Standardinitialisierung eine leere Zeichenkette.
Quelltext 15. Zeilen aus der Datei point15.h [Snippet: PointColor] 
 1class Point {
 2public:
 3// ...
 4    std::string getColor() const;
 5// ...
 6    void setColor(std::string color);
 7private:
 8// ...
 9    std::string mColor{"black"}; (1)
10};
1 Initialisierung (und Typumwandlung) des Datenelementes mColor durch das C-String-Literal "black"

3.3. Ausgabe von Objekten des Types Point

Eine Anwendung der Klasse std::string wäre auch die Darstellung eines Punktobjektes im SVG-Format. Dazu müssen wir aber noch festlegen, wie der mathematische Punkt durch ein SVG-Element circle dargestellt werden soll:.

  • Konvertierung der mathematischen Koordinaten in Koordinaten der Zeichenebene

    • Umwandlung der Fließkommawerte in Pixelkoordinaten durch Runden und Typkonversion double → int

  • Ausdehnung in der Zeichenebene

    • Alle Punkte haben einen fixen Radius für das circle-Element

  • Umwandlung eines Point-Objektes in eine SVG-Zeichenkettendarstellung

    • Einführung einer Beobachterfunktion std::string toSVG() const

3.3.1. Klassenattribute

Klassenattribute werden in C++ als static Datenelemente einer Klasse deklariert. Wird nur das Schlüsselwort static verwendet, so handelt es sich um eine Deklaration. Dies bedeutet, dass die Definition noch (genau einmal) in der Implementierungsdatei erfolgen muss. Dies wiederum kann umgangen werden, indem noch zusätzlich das Schlüsselwort inline verwendet wird. Damit handelt es sich zwar um eine Definition in einer Headerdatei, die aber nicht zur Verletzung der One Definition Rule führt.

Quelltext 16. Zeilen aus der Datei point16.h [Snippet: PointClassmember] 
1class Point {
2public:
3// ...
4private:
5// ...
6    inline static int mSVGRadius{10}; (1)
7};
1 (inline) Definition der Klassenvariable (→ static)

Der inline Spezifizierer bei Variablendeklarationen ist seit C++17 möglich und spart die redundante und fehleranfällige Definition.

3.3.2. Noch eine Beobachterfunktion

Die öffentliche Beobachterfunktion std::string toSVG() const soll aus dem aktuellen Zustand eines Point-Objektes ein std::string-Objekt generieren. Die Deklaration erfolgt in point16.h:

Quelltext 17. Zeilen aus der Datei point16.h [Snippet: PointSVG] 
1class Point {
2public:
3// ...
4    std::string toSVG() const;
5// ...
6private:
7// ...
8};

Die Defintion in point16.cc:

Quelltext 18. Zeilen aus der Datei point16.cc [Snippet: svg] 
1std::string Point::toSVG() const {
2    std::string svgString = "<circle "; (1)
3    svgString += "cx=\"" + std::to_string(Math::toInt(mX)) + "\" ";
4    svgString += "cy=\"" + std::to_string(Math::toInt(mY)) + "\" ";
5    svgString += "r=\"" + std::to_string(mSVGRadius) + "\" "; (2)
6    svgString += "stroke=\"" + mColor + "\" "; (3)
7    svgString +=  "/>";
8    return svgString;
9}
1 Definition der lokalen Variable svgString und Initialisierung mit einem C-String-Literal
2 Umwandlung eines primitiven DT in ein std::string-Objekt
3 Operatoren =` und ` für den Typ std::string und implizite Konvertierung von C-String → std::string

Der Datentyp std::string unterstützt die Konkatenation durch die Operatoren =` und `.

Alle numerischen DT lassen sich durch die freie Funktion std::to_string in ein Objekt des Typs std::string konvertieren. Dies hätte auch mit den Koordinaten, den Datenelementen mX und mY vom Typ double gemacht werden können. Es sollen aber ganzzahlige Pixelkoordinaten in der SVG-Repräsentation verwendet werden. Daher müssen die Fließkommawerte der mathematischen Koordinaten in Pixelkoordinaten gerundet werden: dafür wird die freie Funktion std::round eingesetzt (s.a. mathematische Funktionen der Standardbibliothek bzw. numerische Standardbibliothek). Nach dem Runden soll zudem der Datentyp in den Typ int konvertiert werden.

Beide Schritte (Runden und Typkonversion) sind in der Standardbibliothek zusammen in einer Funktion nicht enthalten, daher schreiben wir eine geeignete Konversionsfunktion in unserer Hilfsklasse Math selbst:

Quelltext 19. Zeilen aus der Datei math.h [Snippet: mathconv] 
1class Math {
2public:
3// ...
4    static int toInt(double value);
5};
Quelltext 20. Zeilen aus der Datei math.cc [Snippet: mathconv] 
1#include <cmath> (1)
2int Math::toInt(const double value) {
3    const double roundedValue{std::round(value)}; (2)
4#ifdef WITH_WARNING (3)
5    return roundedValue; (4)
6#else
7    return static_cast<int>(roundedValue); (5)
8#endif
9}
1 Diese Header-Datei wird u.a. für die Funktion std::round() benötigt
2 Definition und Initialisierung der lokalen Variabe roundedValue mit dem Ergebnis des Funktionsaufrufs std::round()
3 Zu Demonstrationszwecken mit dem Schalter -DWITH_WARNING kompilieren
4 implizite einengende Konversion von double → int
5 explizite einengende Konversion von double → int
Einengende Typkonversionen
Die Sprache C++ ist berühmt für die möglichen impliziten Typkonversionen. Dazu zählen leider auch einengende Konversionen, bei denen der Wert verändert wird.

Wir kompilieren unsere Quelle immer mit der höchsten Warnstufe, die der jeweilige Compiler bietet. Alle Warnungen sind ernst zu nehmen; ein Programm sollte ohne jegliche Warnung kompilieren.

Ausgabe 4: Ausgabe einer Warnung des Compilers bei einer einengenden impliziten Typkonversion
math.cc: In static member function 'static int Math::toInt(double)':
math.cc:39:12: warning: conversion from 'double' to 'int' may change value [-Wfloat-conversion]
   39 |     return roundedValue; // <> *implizite* einengende Konversion von `double` -> `int`
      |            ^~~~~~~~~~~~

 3    if (p.toSVG() != "<circle cx=\"0\" cy=\"0\" r=\"10\" stroke=\"black\" />") return false;
