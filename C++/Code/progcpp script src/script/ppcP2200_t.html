2. Rohe Arrays: Zeiger als Iteratoren

Im Kapitel über rohe Arrays hatten wir schon gesehen, wie man mit Hilfe eines Zeigers auf das erste Array-Element eine Iteration über alle Elemente eines rohen Arrays durchführen kann. Das folgende Bild gibt die Speichersituation hierfür wieder:

Bild 1. Ein rohes Array mit n Elementen in C++ mit einem Zeiger auf das erste Element

Das folgende Beispiel demonstriert eine mögliche Form der Iteration über das statische, rohe Array:

Quelltext 1. Zeilen aus der Datei ppc2200.cc [Snippet: static] 
1const int length = 3;
2int staticArray[length] = {1, 2, 3}; (1)
3const int* iterator1 = &staticArray[0]; (2)
4for(size_t i = 0; i < length; ++i) { (3)
5    std::cout << *iterator1++ << std::endl; (4)
6}
1 a ist der Bezeichner eines statischen, rohen Arrays
2 iterator1 wird mit der Adresse des ersten Array-Elementes initialisiert
3 Mit Hilfe der Längenangabe length kann die Zählschleife formuliert werden
4 Durch die Zeigerarithmetik erhält iterator1 jeweils die Adresse des nächsten Elementes

Selbstverständlich kann man auch mit einem dynamischen, rohen Array arbeiten:

Quelltext 2. Zeilen aus der Datei ppc2200.cc [Snippet: dynamic] 
1std::unique_ptr<int[]> dynamicArray = std::make_unique<int[]>(2 * length); (1)
2const int* iterator2 = &dynamicArray[0]; (2)
3for(size_t i = 0; i < 2 * length; ++i) { (3)
4    std::cout << *iterator2++ << std::endl;
5}
1 Die Erzeugung eines dynamischen Arrays: natürlich verwenden wir einen intelligenten Zeiger (UP), um eine korrekte Speicherverwaltung zu erreichen. Zudem verwendet std::make_unique ein value-initialization.
2 iterator2 wird mit der Adresse des ersten Array-Elementes initialisiert
3 Achtung: die richtige Länge verwenden!

Eine wichtige Eigenschaft der rohen Arrays in C++ ist, dass sie einen zusammenhängenden Speicherbereich belegen. Man kann also das zu bearbeitende Intervall auch durch einen Zeiger auf das erste und durch einen Zeiger auf das letzte Array-Element definieren.

Bild 2. Ein rohes Array mit n Elementen in C++ mit einem Zeiger auf das erste Element und auf das letzte Element als Intervalldefinition

Eine Iteration kommt dann ohne explizite Zählvariable aus:

Quelltext 3. Zeilen aus der Datei ppc2200.cc [Snippet: iterator1] 
1const int* beginIter1 = &staticArray[0]; (1)
2const int* endIter1 = &staticArray[length - 1]; (2)
3for(const int* iterator = beginIter1; iterator <= endIter1; ++iterator) {
4    std::cout << *iterator << std::endl;
5}
1 beginIter1 wird mit der Adresse des ersten Array-Elementes initialisiert.
2 endIter1 wird mit der Adresse des letzten Array-Elementes initialisiert.

Die etwas ungewöhnliche Formulierung des Schleifenbedingung im obigen Beispiel (es muss dort der < =-Operator statt des <-Operators verwendet werden) lässt sich durch folgende Modifikation beseitigen: statt die Adresse des letzten Elementes benutzen wir die Adresse des nicht-existierenden Elementes nach dem letzten Element!

Bild 3. Ein rohes Array mit n Elementen in C++ mit einem Zeiger auf das erste Element und auf ein nicht-existierendes Element nach dem letzten Element

Damit können wir die Iteration in der for-Schleife folgendermaßen formulieren:

Quelltext 4. Zeilen aus der Datei ppc2200.cc [Snippet: iterator2] 
1const int* beginIter2 = &staticArray[0]; (1)
2const int* endIter2 = &staticArray[length - 1] + 1; (2)
3for(const int* iterator = beginIter2; iterator != endIter2; ++iterator) {
4    std::cout << *iterator << std::endl;
5}
1 beginIter2 wird mit der Adresse des ersten Array-Elementes initialisiert.
2 endIter2 wird mit der Adresse des nicht-existierenden eins-nach-dem-letzten Array-Elementes initialisiert.

Die Definition eines Iterationsbereiches mit dem ersten, dazugehörenden Anfang-Element A und einem nicht mehr dazugehörenden (nicht-vorhandenen) Ende-Element E entspricht einem mathematischen halboffenen Intervall

3. Design der Standardbibliothek

Alle Algorithmen der Standardbibliothek, die auf Intervallen basieren, verwenden halboffene Intervalle. Wir haben oben gesehen, wie wir ein solches halboffenes Intervall durch zwei Zeiger definieren.

3.1. Zeiger als Iteratoren für Algorithmen

Die Dokumentation zum einfachen Füll-Algorithmus std::fill beschreibt, dass hier ein Iterator-Paar verlangt wird, um ein halboffenes Intervall zu definieren, dessen Elementwerte dann mit dem Wert des dritten Parameters gefüllt werden.

Quelltext 5. Zeilen aus der Datei ppc2201.cc [Snippet: fill] 
1const int length = 3;
2int staticArray[length] = {1, 2, 3};
3int* beginIter = &staticArray[0]; (1)
4int* endIter = &staticArray[length - 1] + 1; (2)
5std::fill(beginIter, endIter, 42); (3)
1 Anfang-Iterator für das Array
2 Ende-Iterator (eins-nach-dem-letzten Element)
3 Der Füll-Algorithmus aus der C++-Standardbibliothek

Diesen Füll-Algorithmus können wir auch gleich verwenden für einen weiteren Konstruktor, der die Elemente des HeapArray mit einem Wert befüllt:

Quelltext 6. Zeilen aus der Datei heaparray30.h [Snippet: fill] 
1explicit HeapArray(size_t size, const ValueType& value) : mSize(size), mData(std::make_unique<ValueType[]>(size)) {
2    assert(mData);
3    std::fill(mData.get(), (1)
4              mData.get() + mSize, (2)
5              value); (3)
6}
1 Ein roher Zeiger als Anfang-Iterator.
2 Ein roher eins-hinter-das-letzte-Element Zeiger als Ende-Itrator.
3 Der Füllwert value

Die C++-Standardbibliothek definiert unterschiedliche Iterator-Kategorien, die durch verschiedene, aufeinander aufbauende Gruppen von Anforderungen (sog. Concepts) gebildet werden. So ist auch der ForwardIterator definiert als ein Datentyp mit den folgenden Eigenschaften:

Forward-Iterator

Dieser Iterator muss alle Anforderungen an einen sog. InputIterator erfüllen:

  • Kopierbarkeit

  • Zerstörbarkeit

  • Vertauschbarkeit

  • Derefenzierbarkeit mit dem Indirektionsoperator *

  • Elementzugriff mit dem Zeiger-Elementzugriffsoperator →

  • Inkrementierbarkeit als pre-increment (++it) und post-increment (it++)

  • Vergleichbarkeit mit == als auch !=

Darüber hinaus:

  • Standardkonstruierbarkeit

Zeigertypen erfüllen diese Anforderungen in trivialer Art und Weise.

3.2. Iteratoren und Intervalle

Andereseits sind Iteratoren nicht notwendigerweise Zeiger! Es kann auch ein anderer Datentyp sein, der die obige Liste an Anforderungen erfüllt. Haben wir etwa einen Container, dessen Elemente nicht-zusammenhängend (wie bei einer Liste) gespeichert werden, können wir trotzdem mit dem Begriff des Iterators arbeiten. Wir abstrahieren vom Begriff des rohen Zeigers, zu einem Objekt, das sich irgendwie merkt, auf welches Element des Containers es aktuell zeigt.

Bild 4. Ein Container (n Elemente) mit Iterator vor und nach einem Inkrement des Iterators

Selbstverständlich muss es auch möglich sein, einen hinter-das-Ende-Iterator (in Zukunft nur noch Ende-Iterator genannt) zu erzeugen, damit der Begriff des halboffenen Intervalls weiterhin gilt.

Bild 5. Ein Container (n Elemente) mit Beginn- und Ende-Iterator (halb-offenes Intervall)

Alle Container der Standardbibliothek bieten die Möglichkeit, mit Hilfe der Elementfunktionen begin() bzw. end() geeignete Iteratoren bereit zu stellen. Für erhöhte Generizität sollten allerdings die freien Funktionen std::begin bzw. std::end verwendet werden. Damit können auch aus statischen, rohen Arrays Iteratorenpaare erzeugt werden (s.a. Beispiel). Lediglich dynamische, rohe Arrays bilden einen Sonderfall, da sie keine Längeninformation (Anzahl der Elemente) zur Verfügung stellen können.

3.3. Iteratoren für eigene Container

Wir betrachten unsere letzte Realisierung der Klasse HeapArray und fügen dieser eine eigene Realisierung eines Iterators hinzu.

Die Elemente unserer Klasse HeapArray liegen zusammengängend im Speicher. Daher würde als Iterator also ein roher Zeiger ausreichen. Um jedoch die Realisierung besser zu verstehen, erzeugen wir eine eigene Klasse dafür.

Weil der Datentyp T der Elemente des Containers HeapArray<T> parametrierbar ist, muss dann auch unser Iterator HeapArrayIterator<T> parametrierbar für den Elementtyp sein. Dieses Klassentemplate kapselt im wesentlichen nur einen Zeiger, der einen Zugriff auf die Elemente des Containers erlaubt: dies ist also eine reine Benutzungsrelation ohne Eigentümerschaft und wird deswegen als roher Zeiger realisiert.

Quelltext 7. Zeilen aus der Datei heaparray30.h [Snippet: iterator] 
1template<typename ValueType>
2class HeapArrayIterator final { (1)
3public:
4    HeapArrayIterator(const ValueType* p = nullptr) : mPtr(p) {}
5private:
6    const ValueType* mPtr = nullptr; (2)
7};
1 Weil der Container HeapArray<T> ein Template ist, muss natürlich der Iterator dazu ebenfalls ein Template sein.
2 Im wesentlichen kapselt dieses Klassentemplate den rohen Zeiger auf die Elemente des Containers.

3.4. Codestruktur

Es liegt natürlich nun nahe, die Iterator-Klasse HeapArrayIterator als geschachtelte Klasse zu realisieren, um den unmittelbaren Zusammenhang zum Container HeapArray auszudrücken. Wenn wir allerdings die Klasse HeapArrayIterator nun zu einer geschachtelten machen, bekommen wir ein Problem mit der Ableitung des Template-Typ-Parameters für die freie Operatorfunktion operator!=():

Quelltext 15. Zeilen aus der Datei heaparray32.h [Snippet: deduc] 
1template<typename ValueType>
2bool operator!=(const typename HeapArray<ValueType>::HeapArrayIterator& lhs, (1)
3                const typename HeapArray<ValueType>::HeapArrayIterator& rhs) {
4    return lhs.mPtr != rhs.mPtr;
5}
1 Dies ist ein sog. non-deducible Kontext, d.h. der Typ ValueType kann nicht ermittelt werden.

Als Merkregel kann man formulieren: taucht ein Template-Typ-Parameter links von einem scope-Operator :: auf, so führt das zu einem non-deducible Kontext und dies ist dann nicht übersetzbar.

So muss dann der Vergleichsoperator != als Elementfunktion formuliert werden:

Quelltext 16. Zeilen aus der Datei heaparray32.h [Snippet: class]

 9            return mPtr != rhs.mPtr;
10        }
11    private:

13    };
14    explicit HeapArray(size_t size) : mSize(size), mData(std::make_unique<ValueType[]>(size)) {

16    }
17// ...
18private:
19    size_t mSize{0};
20    std::unique_ptr<ValueType[]> mData;
21};

5.3. Lambda-Ausdrücke




Benötigt man ein Funktionsobjekt nur an einer Stelle im Code, so wäre es sehr unpraktisch, wenn man dafür
eine Funktorklasse schreiben müsste. In dem obigen Beispiel wäre es wünschenswert, das
Funktionsobjekt, das durch den Konstruktor-Aufruf Equals<int>(2) aus dem Klassentemplate Equals<T>
erzeugt wird, durch einen sehr kompakten Ausdruck an der Stelle erzeugen zu können. Genau das
leisten die sogenannten Lambda-Ausdrücke.














Anonyme Funktionsobjekte




Mit Lambda-Ausdrücken kann man sog. Closure's generieren.






    

  • 

    Ein Closure ist ein Funktionsobjekt und kann damit mit dem Aufruf-Operator aufgerufen werden.
    

    • 

  • 

    Es hat eine Parameterliste und einen Rückgabetyp.
    

    • 

  • 

    Es kann Bezeichner vom umgebenden Block in den Funktionskörper binden.
    

    • 

  • 

    Jedes Closure hat einen sog. Closure-Typ, den man aber nicht angeben kann bzw. muss (daher auto).
    

    •
