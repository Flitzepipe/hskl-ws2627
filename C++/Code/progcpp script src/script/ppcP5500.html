3. Speichermodell

Ab der C++11 hat die Sprache C++ ein wohldefinertes Speichermodell (s.a. Abschnitt 5.3). Hier sind vor allem Fragen der Nebenläufigkeit geklärt: es ist klar geregelt, was erlaubt ist und was nicht ( und demzufolge undefined behaviour (UB)) ergibt. Damit gibt es eben auch ein wohldefiniertes Verhalten des Programm und zwar unabhängig vom Betriebssystem oder dem Compiler-Hersteller.

3.1. Nebenläufigkeit

Der nebenläufige Zugriff auf dieselbe Speicherzelle mit mindestens einer schreibenden Operation ist in C++ nur unter ganz bestimmten Bedingungen erlaubt (s.a. Data races). Diese sind:

  • diese Zugriffe finden in demselben Aktivitätsträger statt (oder Signal-Handler), oder

  • es handelt sich um atomare Operationen (s.a. std::atomic), oder

  • diese Zugriffe finden in einer happens-before Beziehung zueinander statt.

In allen anderen Fällen beinhaltet das Programm undefined behaviour!

3.2. Was bedeutet volatile

Grundsätzliche Betrachtungen → müssen noch eingearbeitet werden

Variablen selbst sollen nicht als volatile deklariert werden: Variablen sind benannte Objekte, und diese Objekte ändern ihren Wert nicht spontan, wie etwa ein HW-Register. Ausschließlich der Zugriff auf eine Variable sollte volatile gekennzeichnet werden, damit er so wie in der abstrakten Maschine geschrieben stattfindet.

Wird eine Variable als volatile gekennzeichnet, so ist jeder Zugriff darauf eben volatile. Dies möchte man jedoch in bestimmten Bereichen nicht wie etwa in ISRs.

Damit kommen die Funktionstemplates std::experimental::volatile_load() und std::experimental::volatile_store() in Betracht. Oder etwa ACCESS_ONCE() aus dem Linux Kernel

Formell gibt es in C/C++ keine ISRs. Aber Signal-Handler kommen dem am nächsten.

Aber: damit sind ISRs immer implementation-defined und können nicht voll standad-konform sein, weil der C/C**-Standard sie nicht vorsieht.

Für die nebenläufige, unsynchronisierte Verwendung bei der Unterbrechung durch eine Signal (hier: interrupt) gibt es den Datentyp sig_atomic_t. Der Zugriff auf solche sig_atomic_t Objekte muss volatile erfolgen (entweder die Variable muss so deklariert sein oder via ACCESS_ONCE() oder die o.g. Funktionstemplates). Aber Achtung: nach wie vor nicht-atomare RMW-Zyklen. Andernfalls ist das UB (Punkt 132 im C-Standard Anhang).

(Achtung: in dem avr-libc Header signal.h ist ein Fehler (keine korrekte Deklaration des Typs sig_atomic_t). Bei AVR ist sig_atomic_t als signed char deklariert. Achtung: signal.h gehört nicht zu einer freestanding Implementierung (im Gegensatz zu hosted Implementierung).

Daraus folgt, dass der Zugriff auf andere DT grundsätzlich nur synchronisiert erfolgen darf, d.h. ein nebenläufiger Zugriff durch eine ISR muss ausgeschlossen werden: ISR-Sperre (Beispiel: int Zähler auf AVR).

Zusätzlich ist in der ISR nur ein Zugriff auf Objekte vom Type sig_atomic_t erlaubt, also nicht UB. Da aber ISRs sowieso implementation-defined sind, kann die Implementierung hier alles erlauben.

Statt eines volatile Zugriffs kann auch eine Memory-Barrier verwendet werden. Eine Memory-Barrier wirkt wie ein Aufruf einer non-inline Funktion: der Compiler analysiert (escape-analysis), ob die Adresse von Variablen den aktuellen Block verlassen konnten, und nur für diese wird eine Materialisierung der load/stores vorgenommen.

__asm__ __volatile__ ("" : : : "memory"); // globale memory-barrier
__asm__ __volatile__ ("" : "+m" (flag));  // nur für `flag`

Dies trifft ja grundsätzlich für globale Variablen zu (sowohl mit internal wie auch external linkage). Zu beachten ist hierbei, dass zunächst der Code in der abstrakten Maschine optimiert wird als streng sequentieller Ablauf.

Allerdings optimiert der avr-gcc zunächst auf der Ebene der abstrakten Maschine etwa ++g;--g; zu einem noop. Damit wird auch ein davor/danach eingesetzte memory-barrier keine load/store erzwingen. Dies ist kein Fehler, sondern eine Folge davon, dass die Analyse immer von einem sequentiellen Programm ausgeht.

Manchmal kann der Optimierer bei einer memory-barrier (nur für eine bestimmte Variable) die Optimierung (etwa Zusammenfassen eine festen Anzahl von Increments zu einem einzige Add) nicht komplett ausführen. Dies scheint ein Fehler (missing optimization) in avr-gcc zu sein.

Die Memory-Barrier für eine spezielle Variable muss als Macro oder Template geschrieben werden.

Die globale Memory-Barrier verhindert komplett eine Optimierung: dies scheint auch ein Fehler im avr-gcc zu sein (missong optimization).

Beispiel: avr5526.c

Dies ist bei AVR deswegen problematisch, weil das Macro ATOMIC_BLOCK() oder auch sei() und cli() eine globale memory-barrier verwenden (müssen). Denn diese Macros sollen auch in der Lage sein, eine kritischen Abschnitt zu definieren. Damit dürfen load/stores nicht über diese Statements hinweg verschoben werden. Dies führt dann aber auch dazu, dass Optimierungen nicht stattfinden, die stattfinden könnten.

Daher die Empfehlung: besser volatile-access (ACCESS_ONCE / volatile_load / volatile_store) zu verwenden.

Weiterhin schaltet ATOMIC_BLOCK() auch global alle Interrupts aus, statt nur den bestreffenden. Daher sollte anstatt ATOMIC_BLOCK spezifisch durch Registerzugriff (die sind ja sowieso volatile) der spezifische Interrupt abgeschaltet werden (das ist bei modernen AVRs auch nur ein Flag). Da dies ein volatile-Zugriiff ist, werden auch weitere volatile-Zugriffe auf die gemeinsam genutzten Variablen nicht umsortiert.

Das Abschalten eines spezifischen Interrupts ist aber meist ein RMW-Zyklus bei AVR. Das ist aufwändig. Daher kann das globale Abschalten der Interrupts per cli/sei Assembler (asm volatile ("cli" : : :)) besser sein. Dies ist dann auch volatile und eine Umsortierung mit anderen volatile-Zugriffen kann nicht stattfinden. Es stellt auch keine Memory-Barrier dar, damit gibt es oben beschriebene Optimierungsproblem nicht.

Auch wenn es nicht sinnvoll erscheint, Variablen als volatile zu deklarieren, so kann man auch so vorgehen. Damit muss der Zugriff nur noch - wie oben - ebenfalls atomar gemacht werden. Allerdings wird in einer ISR dann auch jeder Zugriff ohne Optimierungen ausgeführt. Um die zu verbessern, könnte man ein un-volatile (const_cast) einsetzen. Eine Modifikation über einen const_cast ist allerdings wieder UB!

Ebenso die Idee über eine union mit volatile und non-volatile Elementen. Das kommt letztlich einem const_cast gleich (s.o.).

SREG ist anders als Cpu.Sreg bei neueren AVRs: SREG ist ein direkter Registerzugriff während Cpu.Sreg mit structure-mapping arbeitet. Seit gcc 4.6.4 führt der direkte Registerzugriff via SREG zu schlechterer Optimierung, das structur-mapping ist da besser.

Beispiel: avr5553.cc / avr5554.c

Im C++-code kann in einer Klasse für die ISR der externe Zugriff außerhalb der ISR mit eine volatile-reference ausgeführt werden. Damit auch keine explizite Memory-Barrier notwendig. Daher beste Optimierung möglich.

3.2.1. Besondere Speicherzellen

Trotzdem gibt es bestimmte Speicherzugriffe bzw. besondere Speicherzellen, die in dieses Modell nicht hineinpassen und deswegen explizit ausgenommen werden müssen.

Solche besonderen Speicherzellen sind bei µC oft:

Register der internen Peripherie

Die Register der internen Peripherie eines µC, etwa die Register zur Steuerung eines UART, sind typischerweise in den normalen Adressbereich (RAM) des µC eingeblendet. Das bedeutet, das das Beschreiben oder Lesen einer festgelegten Adresse nicht im RAM stattfindet, sondern einen Effekt auf das Register der Hardware-Komponente hat.
Speicher mit mehr als einer Adresse

Manche Speicherzellen haben mehrere Adressen im Adressbereich des µC.

Bei diesen beiden Arten von besonderen Speicherzellen (Adressen) treten einige Besonderheiten auf:

  • Hardware-Register ändern spontan ihren Wert:

    • Beispiel: UART-Datenempfangsregister

    • Beispiel: Timer-Overflow-Flag

  • Hardware-Register haben Seiteneffekte:

    • Beispiel: das Beschreiben des UART-Datensenderegisters löst einen Datentransferaus

    • Beispiel: das Beschreiben eines Flags (Bits) setzt dieses Flag zurück

  • Hardware-Register sind semantisch abhängig voneinander

    • Beispiel: Initialisierung einer Hardware-Komponente: Schreib- oder Lesevorgänge müssen in einer bestimmten Reihenfolge - so wie im Code - ausgeführt werden

Tabelle 1. Unzulässige Optimierung: Werte der Hardware-Register können nicht als stabil angenommen werden
Quelltext 1. Original
std::byte v1{}, v2{};
v1 = *uartDataRegister;
v2 = *uartDataRegister;
Quelltext 2. Unzulässige Optimierung
std::byte v1{}, v2{};
v1 = *uartDataRegister;
v2 = v1;

Wenn nun Hardware-Register spontan ihren Wert ändern, so kann der Compiler nicht mehr annehmen, dass v1 und v2 denselben Wert haben, und daher das Lesen nicht mehr optimieren zu:

Tabelle 2. Unzulässige Optimierung: Lesevorgänge von Hardware-Registern nach Schreibvorgängen können nicht als stabil angenommen werden
Quelltext 3. Original
std::byte v1{};
*uartControlRegister = 0x01;
v1 = *uartControlRegister;
Quelltext 4. Unzulässige Optimierung
std::byte v1{};
*uartControlRegister = 0x01;
v1 = 0x01;

Auch können Abfragen nicht mehr aus einer Schleife heraus gezogen werden, weil der Compiler nicht davon ausgehen kann, dass der Wert unverändert bleibt:

Tabelle 3. Unzulässige Schleifenoptimierung
Quelltext 5. Original
while(*uartFlagRegister & 0x01) {
    // ...
}
Quelltext 6. Unzulässige Optimierung
if(*uartFlagRegister & 0x01) {
    do {
        // ...
    } while(true);
}

Weil Hardware-Register Seiteneffekte haben, etwa eine Hardware-Komponente starten, darf ein einmaliger Schreibvorgang auch dann nicht weg-optimiert werden, selbst wenn dieses Hardware-Register niemals mehr im Code gelesen wird.

Tabelle 4. Hardware-Register haben Seiteneffekte, daher darf das Beschreiben nicht weg-optimiert werden.
Quelltext 7. Original
*uartControlRegister = 0x01; // Uart aktivieren
Quelltext 8. Unzulässige Optimierung
Tabelle 5. Hardware-Register haben Seiteneffekte, daher dürfen Modifikationen nicht zusammengefasst werden
Quelltext 9. Original
*uartControlRegister = 0x01; // Uart aktivieren
*uartControlRegister = 0x02; // TX einschalten
Quelltext 10. Unzulässige Optimierung

*uartControlRegister = 0x02;

Schreib- oder Lesevorgänge an Hardware-Registern haben semantische Abhängigkeiten, daher darf die Reihenfolge in keinem Fall vom Optimierer geändert werden.

Tabelle 6. Zwischen Hardware-Registern gibt es semantische Abhängigkeiten
Quelltext 11. Original
*uartConfigRegister = 0xf0;  // zuerst konfigurieren,
*uartControlRegister = 0x01; // dann aktivieren
Quelltext 12. Unzulässige Veränderung
*uartControlRegister = 0x01;
*uartConfigRegister = 0xf0;

Alle diese Optimierungen unterbindet das Schlüsselwort volatile.

Quelltext 13. Korrekte Definition und Verwendung eines Hardware-Registers
volatile std::byte* const uartControlRegister = reinterpret_cast<volatile std::byte*>(0x0100);
*uartControlRegister = 0x01;

Natürlich kann man jeder beliebige Variable (benanntes Objekt) als volatile deklarieren. Jedoch ist dies für alles andere als Hardware-Register falsch. Denn dadurch werden viele, bei normalen Speicherzellen mögliche Optimierungen unterbunden (s.a. Abschnitt 5.3).

3.2.2. volatile bedeutet nicht auch atomar

Die Qualifizierung von Variablen mit volatile ist auch deswegen falsch, weil dies oft mit atomar gleichgestellt wird. Aber volatile bedeutet nicht auch atomar. Wie in Abschnitt 3.2.1 gezeigt, unterbindet volatile nur die Optimierungen, die für normale Speicherzugriffe möglich sind.

Tabelle 7. volatile ist kein Ersatz für atomare Operationen
Quelltext 14. Interrupt-Service-Routine / globale Variable
volatile int v; (1)
ISR() {
    v += 1; (2)
}
1 v ist kein Hardware-Register, daher ist volatile hier falsch
2 Ein read-modify-write ist nicht-atomar. Eine Unterbrechung durch eine weitere ISR ist möglich.
Quelltext 15. Anderswo im Programm
void f() {
    if (v == 256) { (1)
        // ...
    }
}
1 Das Lesen von v geschieht nicht-atomar. Eine Unterbrechung durch die ISR ist möglich.

Da Operationen auf Hardware-Registern unbedingt so wie im Code ausgeführt werden müssen, können sie nicht mittels normaler Operationen auf Speicherzellen ausgeführt werden. Die zahlreichen möglichen Optimierungen verhindern dies.

Auch für atomare Operationen via std::atomic können noch einige Optimierungen vom Compiler ausgeführt werden. Daher scheiden auch diese aus für Hardware-Register Zugriffe. Zudem ist im allgemeinen auch gar keine Atomartät für Hardware-Register gefordert.

Nur volatile unterstützt alle notwendigen Eigenschaften für Hardware-Register Operationen.

Auf der anderen Seite eignen sich volatile Objekte nicht für den nebenläufigen Zugriff (per Interrupt-Service-Routine oder mit mehreren Aktivitätsträgern). Ihnen fehlt zum einen Atomarität und zum anderen erlaubt der C++-Standard konflikt-behafteten Zugriff (read-write, write-read, write-write) nur via std::atomic oder mit kritschen Abschnitten (s.a. std::mutex) (read-read Situationen sind erlaubt auch für normale wie auch für volatile Objekte) bzw. durch Abstellen der Nebenläufigkeit (bspw. Deaktivieren der Interrupts) und Sicherstellen einer Memory-Barrier.

4. Nebenläufigkeit auf einfachen µC

Haben wir einen µC mit einer CPU mit nur einem Kern, so ist die einzige Form von Nebenläufigkeit das Ausführen von Interrupt-Service-Routinen. Ist also das Behandeln von Interrupts eingeschaltet, so entsteht dadurch eine Form von Nebenläufigkeit. Entsprechend kann auf Nebenläufikeit verzichtet werden, wenn bspw. die Behandlung von allen möglichen bzw. verwendeten Interrupts abgeschaltet wird.

4.1. Interrupt-Service-Routinen (ISR)

Das folgende Beispiel Quelltext 16 enthält einige Fehler und Unklarheiten:

  • Die Funktion isr() soll eine Interrupt-Service-Routine sein. Es ist jedoch unklar, zu welcher Hardware-Komponente und welchem Interrupt davon diese dann zugrordnet werden soll. Diese Zuordnung kann nur hardware-spezifisch (für den konkreten µC) erfolgen.

  • Die übersetzungseinheit-globale Funktion isr() ist in dieser Übersetzungseinheit unbenutzt: der Compiler wird sie daher entfernen.

  • Es ist nicht klar, ob die Funktion isr() wiederum durch andere oder denselben Interrupt unterbrochen werden kann. Falls ja, so ist die Anweisung v += 1; falsch, das sie nicht als atomar angesehen werden kann. Diese Einstellungen sind wieder hardware-spezifisch.

  • In der Funktion main() wird auf v zugegriffen, allerdings wieder nicht atomar (werder beim Vergleich noch beim Inkrement). Dies ist falsch, weil die Funktion isr() als Interrupt-Service-Routine auch v nebenläufig zugreift.

 2    int v; (1)
 3    void isr() { (2)
 4        (3)
 5        v += 1; (4)
 6    }
 7}
 8int main() {

3 Weil diese Funktion nur übersetzungseinheit-global ist und hier nicht benutzt wird, wird sie nicht erzeugt. Es besteht hier auch kein Zusammenhang zu einer Hardware-Komponente und dessen Interrupt-Möglichkeiten.
4 Es kann nicht davon ausgegangen werden, dass dieses RMW atomar stattfindet.
5 Der folgende Code kann durch einen Interrupt unterbrochen werden: somit findet die Ausführung der isr() nebenläufig statt.
6 Es kann nicht davon ausgegangen werden, dass das Lesen von v atomar stattfindet. Weiterhin besteht hier ggf. ein semantisches Problem, weil natürlich auch das folgende Inkrement nicht atomar mit dem Vergleich stattfindet, also auch andere Werte als 43 entstehen können.
7 Es kann nicht davon ausgegangen werden, dass dieses RMW atomar stattfindet.

Weil nun einige Grundvoraussetzungen für die korrekte Nebenläufigkeit in diesem Beispiel nicht gegeben sind, führen die korrekten Optimierungen, die auf diesen Annhamen beruhen, zu fehlerhaften Auswirkungen dieser Optimierungen:

  • Die Funktion isr() wird komplett entfernt, weil der Compiler sie als unbenutzt erkennt.

  • Das Laden des Wertes von v wird aus der Schleife heraus gezogen, weil der Compiler annimmt, das v unverändert bleibt. In diesem speziellen Fall in v eine übersetzungseinheit-globale Variable, also nur in dieser einen Übersetzungseinheit sichtbar. Daher kann der Compiler folgern, dass v nicht verändert wird, denn auch isr() wird nicht aufgerufen.

  • Das Inkrement v += 1 wird durch die Konstante 43 ersetzt, weil der Compiler annimmt, das v unverändert bleibt.

  • Es entsteht eine leere endlos Schleife (Diese Endlos-Schleife ohne Seiteneffekte ist streng genommen auch undefined behaviour. Das spielt an dieser Stelle aber keine Rolle. ).

Der Compiler analysiert den Programmablauf mit folgenden Annahmen:

  • Das Programm startet in main()

  • Das Programm besitzt nur einen Aktivitätsträger beginnend in main(), es wird also streng sequentiell abgearbeitet.

Dies führt zu folgenden Folgerungen:

  • Da main() keine weitere non-inline Funktion (eine Funktion, deren Definition nicht sichtbar ist) aufruft, kann es keine Änderungen an v gegeben.

  • Da isr() nicht aus main() aufgerufen wird (und auch keine weitere non-inline Funktion, die ggf. isr() aufrufen könnte), nimmt der Compiler an, das isr() nicht aufgerufen wird (obwohl als used markiert, dies veranlasst ihn aber nicht, die Funktion in die Ablaufanalyse mit einzubeziehen).

  • Da der Compiler nur eine sequentielle Analyse durchführt, gibt es keine Möglichkeit mehr wie isr() ablaufen könnte.

Damit bleibt eine leere Endlosschleife in main().

4.2. Grenzen der Optimierung

4.2.1. Escape-Analysis

Wird in die Schleife in main() der Aufruf einer Funktion eingefügt, die der Compiler nicht analysieren kann, weil ihre Definition nicht in dieser Übersetzungseinheit ist, so ist die sog. Escape-Analyse an dieser Stelle nicht möglich. Der Compiler muss daher annehmen, dass f() die Variable v ändert. Denn f() kann auf die übersetzungseinheit globale Variable v zugreifen.

Quelltext 21. Zeilen aus der Datei avr5507b.cc 
 1#include <avr/interrupt.h>
 2#include <atomic>
 3#include <avr/memory.h>
 4namespace {
 5    int v; (1)
 6    void f(); (2)
 7}
 8void isr() __asm__("__vector_5") __attribute__ ((__signal__, __used__, __externally_visible__));
 9void isr() {
10    v += 1; (3)
11}
12int main() {
13    while(true) {
14        f(); (4)
15        (5)
16        if (v == 42) { (6)
17            v += 1; (7)
18        }
19    }
20}
1 Übersetzungseinheit-globale Variable v wird nebenläufig, gemeinsam genutzt von isr() und main()
2 Deklaration einer nur lokal sichtbaren non-inline Funktion f()
3 Es kann nicht davon ausgegangen werden, dass dieses RMW atomar stattfindet.
4 Der Aufruf einer non-inline Funktion unterbindet hier die Escape-Analyse des Compilers: als Konsequenz kann der Compiler hier nicht mehr davon ausgehen, dass v unverändert bleibt.
5 Der folgende Code kann durch einen Interrupt unterbrochen werden: somit findet die Ausführung der isr() nebenläufig statt.
6 Es kann nicht davon ausgegangen werden, dass das Lesen von v atomar stattfindet. Weiterhin besteht hier ggf. ein semantisches Problem, weil natürlich auch das folgende Inkrement nicht atomar mit dem Vergleich stattfindet, also auch andere Werte als 43 entstehen können.
7 Es kann nicht davon ausgegangen werden, dass dieses RMW atomar stattfindet.

Dies führt dann dazu, dass das Laden von v tatsächlich in der Schleife stattfindet.

4.2.2. Memory-Barrier

Ein Memory-Barrier ist im Effekt vergleichbar mit dem Aufruf einer non-inline Funktion (s.o.). Der Optimierer des Compilers betrachtet alle Variablen, auf die von außerhalb der betrachteten Funktion zugegriffen werden kann, als modifiziert.

In dem folgenden Beispiel handelt es sich immer noch um die globale Variable v: diese ist in main() verwendet, da sie jedoch global ist, nimmt der Optimizer nun an, dass sie anderweitig geändert wurde. Daher muss v in jedem Durchlauf der Schleife neu geladen werden.

Quelltext 34. Zeilen aus der Datei avr5507.cc [Snippet: main] 
1int main() {
2    while(true) {
3        _MemoryBarrier(); (1)
4        (2)
5        if (v == 42) { (3)
6            v += 1; (4)
7        }
8    }
9}
1 Fügt eine Compiler-memory-barrier ein.
2 Der folgende Code kann durch einen Interrupt unterbrochen werden: somit findet die Ausführung der isr() nebenläufig statt.
3 Es kann nicht davon ausgegangen werden, dass das Lesen von v atomar stattfindet. Weiterhin besteht hier ggf. ein semantisches Problem, weil natürlich auch das folgende Inkrement nicht atomar mit dem Vergleich stattfindet, also auch andere Werte als 43 entstehen können.
4 Es kann nicht davon ausgegangen werden, dass dieses RMW atomar stattfindet.

Man sieht nun, dass in der Schleife jeweils v neu geladen wird. Dies findet im if(…​)-Staement statt.

Quelltext 35. Zeilen aus der Datei avr5507.S [Snippet: main]
 1main:
 2	ldi r24,lo8(43)	 ;  tmp46,
 3	ldi r25,0		 ; 
 4.L3:
 5	lds r18,(anonymous namespace)::v	 ;  v, v
 6	lds r19,(anonymous namespace)::v+1	 ;  v, v
 7	cpi r18,42	 ;  v,
 8	cpc r19,__zero_reg__	 ;  v
 9	brne .L3		 ; ,
10	sts (anonymous namespace)::v,r24	 ;  v, tmp46
11	sts (anonymous namespace)::v+1,r25	 ;  v, tmp46
12	rjmp .L3		 ;

Allerdings haben wir nach wie vor das semanstische Problem, dass der Vergleich und das Inkrement nicht-atomar miteinander sind.

Auf den einfachen µC der AVR-Familie (Ein-Kern ohne Instruction-Reordering) existiert dafür das folgende Macro:

#define _MemoryBarrier() __asm__ __volatile__("":::"memory")

Diese bewirkt nur eine Compiler-Memory-Barrier. Eine CPU-Memory-Barrier wird von der AVR-CPU gar nicht unterstützt.
