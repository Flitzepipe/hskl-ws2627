2. Daten im Speicher

Achtung: Java-Programmierer
Im folgenden wir der Begriff der Referenz verwendet. Dieser ist im Kontext von C++ aber mit einer fundamental anderen Bedeutung belegt als im Kontext von Java!

2.1. Variablen und Referenzen

Variablen
Im Abschnitt über Datentypen, Objekte und Werte haben wir Variablen als Objekte mit Namen oder benannte Objekte definiert. Damit hat eine Variable die wichtigen, untrennbaren Eigenschaften: Name, Speicherbereich, Typ und Bitfolge. Das kann man sich im Speicher folgendermaßen vorstellen:
Bild 1. Variablen und ihr Speicher

Der Begriff der Referenz [1] bedeutet allgemein: sich beziehen auf. Im obigen Beispiel bezieht sich der Name a auf das Objekt an der Adresse 0x0100, Länge 4 Bytes, mit dem Typ int und einer Bitfolge, die dem Wert 0 entspricht.

Referenz
Eine Referenz in C++ ist also nur eine Zuordnung eines Namen zu einem Objekt. Man kann sogar beliebig viele Namen für ein Objekt vergeben; und alle diese Namen sind gleichwertig.

Syntaktisch wird in C++ allerdings zwischen dem ersten Namen bei der Definition der Variablen (Definitions-Anweisung → Bereitstellung von Speicher) und den weiteren Namen unterschieden (Deklarationen):

int   a  = 0; (1)
int&  ra = a; (2)
1 Definition und Initialisierung eines int-Objektes mit dem Namen a → Variable a
2 Deklaration einer Referenz ra (noch ein Name) für das int-Objekt, dass schon den Namen a hat.
Notation in Deklarationsanweisungen für Referenzen

Es gibt unterschiedliche, aber gleichwertige Möglichkeiten, die Deklarationsanweisung für Referenzen zu notieren:

int   a  = 0;
int&  ra1 = a; (1)
int & ra2 = a;
int  &ra3 = a;
1 empfohlene Variante

Das Symbol & hat viele Semantiken (bspw. auch als Adressoperator). Um Verwechslungen auszuschließen, sollte die Variante int& verwendet werden: dies kann man dann (von rechts nach links) als Referenz für ein int-Objekt lesen.
Bild 2. Deklaration einer weiteren Referenz für ein Objekt

Das folgende Beispiel zeigt die Deklaration mehrerer Referenzen für ein Objekt. Alle diese Refrenzen sind gleichwertig!

Vorsicht
Nicht alles, was möglich ist, soll man auch tun: lokalen Variablen mehrere Referenzen (Namen) zu geben, ist einfach nur verwirrend. Aber bei Funktionsparametern (und später anderen Stellen) ist es sehr sinnvoll!

3. Parameterübergabe bei Funktionen

Achtung
Java kennt nur eine Variante der Parameterübergabe an Methoden: call-by-value. Bislang haben wir auch hier im eigenen Code⁠[2] nur dieses Verfahren eingesetzt. Dieses Verfahren ist aber nicht immer sinnvoll!

3.1. Das sog. call-by-value-Verfahren der Parameterübergabe

Die folgende Grafik verdeutlicht nochmals das bekannte Verfahren call-by-value: der Wert an der Aufrufstelle wird bestimmt (evaluiert) und in die Parameter-Variable kopiert:

Bild 3. Parameterübergabe (und Ergebnisrückgabe) als call-by-value

Dasselbe passiert bei der Ergebnisrückgabe.

3.2. Das sog. call-by-reference-Verfahren der Parameterübergabe

Hier wird in der Parameterliste der Funktion ein Referenz-Parameter deklariert: der Typ der Referenz muss natürlich mit dem Typ des Wertes an der Aufrufstelle übereinstimmen. Damit ist der Name des Parameters nur ein weiterer Name für das Objekt (benannt oder unbenannt) an der Aufrufstelle.

Bild 4. Parameterübergabe als call-by-reference (Ergebnisrückgabe by-value)

An der Grafik wird folgendes deutlich:

  • mit Referenz-Parametern vermeidet man Objekt-Kopien! Man stelle sich einen sehr langen String vor, der bei call-by-value kopiert würde. Bei call-by-reference findet aus Programmierersicht nichts statt!

  • wird über den Referenz-Parameter ein Wert zugewiesen (analog zu dem obigen Beispiel mit nur lokalen Variablen), so wirkt sich das selbstverständlich auf das referenzierte Objekt aus, und das ist das Objekt / Variable im Aufrufer!

Das folgende Beispiel macht diesen Effekt deutlich:

Quelltext 2. Zeilen aus der Datei ppc0403.cc (einige Zeilen nicht dargestellt)
 1#include "../ppc.h"
 2#include <iostream>
 3class A {
 4public:
 5    void foo(int& x) { (1)
 6        x = 42;
 7    }
 8};
 9int main() {
10    A o;
11    int a{0};
12    o.foo(a);
13}
1 Input/Output-Parameter x
Ausgabe 2. Ausgabe des Programms: ppc0403
int main() a=0
void A::foo(int&) x=0
void A::foo(int&) x=42
int main() a=42
Input-Parameter und Output-Parameter

Weil ein Objekt, was in einer Parameterliste einer Funktion mit einer (nicht-konstanten) Referenz bezeichnet (entgegengenommen) wird, durch diese Funktion geändert werden kann, bezeichnet man diese Art auch oft als Output-Parameter: es wird ein Wert in dem referenzierten Objekt des Aufrufers zurückgegeben. Wird der Wert des Objektes vor dem Aufruf von der Funktion verwendet, so spricht man auch von Input/Output-Parameter.

Input-Parameter sind hingegen die kopierenden Parameter (keine Referenz) oder konstante Referenzen.

4. Konstante Referenzen (Variablen)

Wäre der positive Effekt, dass auf eine Objektkopie verzichtet wird, immer mit der Semantik eines Output- Parameters verbunden, würde das eine große Fehlerquelle bedeuten. Eines der wichtigsten Schlüsselwörter in C++ ist daher const bzw. die damit verbundene const-Correctness!

4.1. Variablen und const

Mit Hilfe des const-Spezifizierers kann man - salopp gesagt - konstante Variablen, also Konstanten definieren.

Genau genommen ist hierbei nicht das Objekt⁠[3] konstant, sondern das Objekt ist über den Bezeichner nicht (nachträglich) änderbar. Aus diesem Grund ist eine Initialisierung obligatorisch.

Quelltext 3. Definition einer konstanten Variablen (→ Konstante)
const int a = 42;

// a = 3; // nicht möglich
Dass man in seinen Programmen keine magischen Literale (etwa 3.14) verwenden sollte, sollte bekannt sein. Von C ist die (Un-) Sitte verbreitet, dafür Präprozessormakros zu definieren. Da dies reiner Textersatz ist, verliert man dadurch die Typsicherheit. Besser ist die Definition von geeineten Klassenkonstanten (s.a. math.h bzw. math.cc)

Besser sagt man zu einer const-qualifizierten Variablen: read-only-Variable. Damit ist klar, dass

  • man sie initialisieren muss, und

  • man anschließlend den Wert nur noch lesen und nicht verändern kann.

Parameter-Variablen sind auch Variablen: sie werden beim Funktionaufruf und call-by-value initialisiert. Gerade bei Funktionen und ggf. etwas längeren Funktionskörpern ist es für das Verständnis sehr gut, wenn man davon ausgehen kann, dass der Wert einer Parametervariablen nicht modifiziert werden / wurde.

Regel: Mache alles const, wenn Du kannst

Diese Regel ist sher wichtig: sie dient dazu, den Code vetsändlicher zu machen und viele Fehler zur Compilezeit schon auf zu decken, wie etwa im folgenden Beispiel. Der Fehler wäre mit void foo(const int a) nicht passiert:

void foo(int a)

if (a = 42) {
}

Die wird in allen Beispielen dieses Skripts ebenfalls angewendet. So auch hier:

Quelltext 4. Zeilen aus der Datei math.cc [Snippet: const] 
1bool Math::equal(const double a, const double b) { (1)
2    const double epsilon{1e-10}; (2)
3    const double difference{a - b}; (3)
4    if ((difference > -epsilon) && (difference < epsilon)) {
5        return true;
6    }
7    return false;
8}
1 Auch die Parametervariablen werden const-qualifiziert. Damit sind es ebenfalls read-only-Variablen, deren Wert in der gesamten Funktion unverändert bleibt.
2 Natürlich werden möglichst alle lokalen Variablen ebenfalls 'const'-qualifiziert.
3 …​ auch hier …​

4.2. Konstante Referenzen

Natürlich kann man auch (weitere) konstante Referenzen für ein Objekt hinzufügen:

Quelltext 5. Definition einer konstanten Referenz
const int  a  = 42;
const int& ra = a;

// ra = 3; // nicht möglich
Semantik einer const-Referenz-Deklaration
Wie oben schon gesagt, ist nicht das Objekt konstant, sondern die Aussage ist: über den Namen in dieser Deklaration will ich das Objekt nicht ändern können.

Daher ist es auch möglich, eine konstante Referenz mit Hilfe einer nicht-konstanten Referenz (Namen) zu deklarieren. Umgekehrt geht das natürlich nicht!

Quelltext 6. Definition einer konstanten Referenz für ein nicht-konstantes Objekt
int  a  = 42;
a = 3; // ok
const int& ra = a;
// ra = 3; // nok
Als Eselsbrücke kann man sich merken: das Hinzufügen von const ist immer möglich!

4.3. Konstante Referenzen in Parameterlisten

Oben haben wir festgestellt, dass es möglich ist, eine const-Referenz für ein non-const-referenziertes Objekt zu deklarieren. Dasselbe Prinzip können wir auch auf Referenzparameter in Parameterlisten anwenden:

Quelltext 7. Zeilen aus der Datei ppc0404.cc (einige Zeilen nicht dargestellt)
 1#include <iostream>
 2class A {
 3public:
 4    void foo(const int& x) { (1)
 5        // x = 42; (2)
 6    }
 7};
 8int main() {
 9    A o;
10    int a{0};
11    o.foo(a);
12}
1 Input-Parameter x
2 nicht mehr möglich

Damit ergeben sich die folgenden Möglichkeiten für einen Parameter:

Wertkopie

für primitive Datentypen (geringe Größe) oder Datentypen, die einfach zu kopieren sind (dazu erfahren wir später mehr) → Input-Parameter
konstante Referenz

für alle nicht-primitiven Datentypen (UDT: user-defined-type) → Input-Parameter
nicht-konstante Referenz

Ausnahme: Input/Output-Parameter

4.4. Konstante Referenzen für UDT und Elementfunktionen

Die Werte von Objekten primitiver Datentypen sind nur durch Zuweisungen änderbar. Dies ist bei konstanten Referenzen nicht möglich (s.o.).

Haben wir eine nicht-konstante Referenz für ein Objekt eines nicht-primitiven DT (UDT), dann gibt es neben der Zuweisung auch noch die Möglichkeit, den Zustand des Objektes über setter (Mutatoren) zu ändern.

Haben wir eine konstante Referenz für ein UDT-Objekt, so darf über diese Referenz der Zustand nicht änderbar sein, d.h. setter müssen unterbunden werden. Hingegen müssen getter dieses Typs nach wie vor möglich sein, denn sie ändern ja den Zustand des Objektes nicht.

Aus diesem Grund unterscheidet C++ streng die getter (Observatoren, Beobachter) von den setter⁠n (Mutatoren), indem die getter-Elementfunktionen die zusätzliche const-Qualifizierung (nach der Parameterliste) bekommen.

Quelltext 8. Zeilen aus der Datei ppc0405.cc 
 1#include <iostream>
 2class A {
 3public:
 4    void setX(const int& x) { (1)
 5        mX = x;
 6    }
 7    int getX() const { (2)
 8        return mX;
 9    }
10private:
11    int mX{0};
12};
13int main() {
14    A a; (3)
15    a.setX(42);
16    const A& ca = a; (4)
17    // ca.setX(3); (5)
18    std::cout << "a.x = " << ca.getX() << std::endl; (6)
19}
1 ein setter (Mutator) ist non-const
2 ein getter (Observator) ist immer const
3 a ist eine non-const Referenz für das Objekt
4 ca ist eine const-Referenz für dasselbe Objekt (a)
5 nicht möglich
6 const Elementfunktion für const-Referenz ist ok
Ausgabe 3. Ausgabe des Programms: ppc0405
a.x = 42

4.5. Parameterlisten und konstante Referenzen für UDT

Das folgende Beispiel demonstriert, was passiert, wenn man versucht, für eine konstante Referenz eine Mutator-Elementfunktion aufzurufen:

Quelltext 9. Zeilen aus der Datei ppc0407.cc

 2class A {

 4    void setX(const int& x) { (1)

5. Details

5.1. Statische Datenelemente (Klassenvariablen) und const

Das Prinzip der Konstanten lässt sich auch gut auf statische Datenelemente anwenden. Da diese ja unveränderbar sind, können sie unbedenklich als public-Klassenkonstanten deklariert werden. Ihr Wert wird bestimmt, bevor in die Funktion main() eingetreten wird. Sie sind vergleichbar mit globalen Konstanten, allerdings im Namensraum der Klasse.

Quelltext 10. Zeilen aus der Datei math.h [Snippet: math] 
1class Math {
2public:
3// ...
4    inline static const double mPi{2.0 * std::acos(0.0)};
5};
Quelltext 11. Zeilen aus der Datei math.cc [Snippet: math] 
1#include "math.h"
2#include <cmath>

5.2. Ergebnisrückgabe bei Funktionen

Wie bei der Parameterübergabe kann man Referenzen auch bei der Ergebnisrückgabe einer (freien) Funktion verwenden. Dabei muss man jedoch Vorsicht walten lassen: es darf nicht passieren, dass das referenzierte Objekt nach der Rückkehr aus der Funktion schon zerstört ist. Primitive Typen werden auch hier als Kopie zurückgegeben.

Im folgenden Beispiel sind korrekte und falsche Anwendungen:

Quelltext 12. Zeilen aus der Datei ppc0406.cc 
 1#include <iostream>
 2#include <string>
 3class A {
 4public:
 5    const std::string& value() const { (1)
 6        return mValue;
 7    }
 8//    std::string& value() const { (2)
 9//        return mValue;
10//    }
11    std::string& wrong() { (3)
12        return mValue;
13    }
14    const std::string& wrong2() const { (4)
15        return mValue + "epilog"; (5)
16    }
17private:
18    std::string mValue = "gaaanz lange Zeichenkette";
19};
20int main() {
21    A a;
22    std::cout << "value = " << a.value() << std::endl; (6)
23    a.wrong() = "Ups"; (7)
24    std::cout << "value = " << a.value() << std::endl;
25    std::string& s = a.wrong(); (8)
26    s = "Ups2"; (9)
27    std::cout << "value = " << a.value() << std::endl;
28}
1 Ein Datenelement (hier: UDT) darf von einer Observator-Funktion als const-Referenz zurückgegeben werden
2 Nicht möglich! Denn damit würde ein Observator ggf. zu einem Mutator
3 Zwei Fehler in diesem Observator: Rückgabe als non-const-Referenz, Observator muss const sein → s.a Fehler in main()
4 Fehler ergibt leider nur eine Warnung bei der Kompilierung
5 Durch den +-Operator entsteht ein temporäres (anonymes) Objekt auf dem Stack, dass beim Verlassen der Funktion zerstört wird
6 Lies: a.value() ist ein weiterer Name für das Datenelement mValue
7 Erscheint ungewöhnlich, ist tatsächlich aber nicht selten. Aber: der Fehler liegt in Klasse A
8 Weniger ungewöhnlich: s ist nun eine non-const-Referenz für das Datenelement A::mValue
9 wieder der Fehler wie oben
Ausgabe 5.
ppc0406.cc: In member function 'const std::string& A::wrong2() const':
ppc0406.cc:35:23: warning: returning reference to temporary [-Wreturn-local-addr]
   35 |         return mValue + "epilog"; // <> Durch den `+`-Operator entsteht ein *temporäres* (anonymes) Objekt auf dem Stack, dass beim Verlassen der Funktion zerstört wird
      |                ~~~~~~~^~~~~~~~~~
Ausgabe 6. Ausgabe des Programms: ppc0406
value = gaaanz lange Zeichenkette
value = Ups
value = Ups2
Regeln für die Ergebnisrückgabe als Referenz

  • Observator-Funktionen müssen mit const qualifiziert werden

    • Dann ist es auch unmöglich, ein Datenelement als non-const-Referenz zurück zu geben

  • Niemals eine lokale Variable oder ein temporäres, anonymes Objekt als Referenz zurückgeben.

    • Beachtet man die Warnungen des Compilers, kann auch das nicht passieren

  • Primitive Datentypen werden kopierend zurückgegeben.

6. Rückblick

Das Prinzip für die Gestaltung von getter (Observatoren) setter (Mutatoren) wenden wir auf die Klasse Point an:

Quelltext 13. Zeilen aus der Datei point30.h [Snippet: getter] 
 1class Point {
 2public:
 3// ...
 4    double getX() const; (1)
 5    double getY() const;
 6    const std::string& getColor() const; (2)
 7    std::string toSVG() const; (3)
 8    static int svgRadius(); (4)
 9// ...
10};
1 Observator ist const, primitive Typen werden per-value zurückgegeben
2 Ergebnis dieses Observators ist eine const-Referenz auf das Datenelement mColor
3 Ergebnisrückgabe als Kopie
4 statische Elementfunktionen können nicht const-qualifiziert werden, denn sie haben keinen Zugriff auf einen Objektzustand
Quelltext 14. Zeilen aus der Datei point30.cc [Snippet: getter] 
 1const std::string& Point::getColor() const {
 2    return mColor; (1)
 3}
 4std::string Point::toSVG() const {
 5    std::string svgString = "<circle ";
 6    svgString += "cx=\"" + std::to_string(Math::toInt(mX)) + "\" ";
 7    svgString += "cy=\"" + std::to_string(Math::toInt(mY)) + "\" ";
 8    svgString += "r=\"" + std::to_string(mSVGRadius) + "\" ";
 9    svgString += "stroke=\"" + mColor + "\" ";
10    svgString += "fill=\"" + mColor + "\" ";
11    svgString +=  "/>";
12    return svgString; (2)
13}
1 Ergebnisrückgabe als const-Referenz erlaubt
2 Ergebnisrückgabe als Wertkopie notwendig

Für das folgende Beispiel erweitern wir den Mutator für die Punktfarbe. Die Elementfunktion setColor() wird überladen:

Quelltext 15. Zeilen aus der Datei point30.h [Snippet: Point] 
1class Point {
2public:
3// ...
4    void setColor(const std::string& color);
5    void setColor(unsigned char r, unsigned char g, unsigned char b);
6// ...
7};

Es erfolgt die folgende Realisierung:

Quelltext 16. Zeilen aus der Datei point30.cc [Snippet: setcolor] 
1void Point::setColor(const std::string& color) {
2    mColor = color;
3}
4void Point::setColor(const unsigned char r, const unsigned char g, const unsigned char b) {
5    mColor = "rgb(" + std::to_string(r) + "," + std::to_string(g) + "," + std::to_string(b) + ")";

Der Mutator void Point::setColor(const std::string& color) ist immer noch nicht gut, da man hier noch beliebige Zeichenkette angeben kann. Besser wäre es, die Eigentschaft der Farbe in einer eigenen Klasse zu kapseln.

Ebenso ist der Mutator void Point::setColor(unsigned char r, unsigned char g, unsigned char b) nicht gut: hier wird in einer Parameterliste dreimal der unspezifische Datentyp unsigned char verwendet. Das birgt Verwechselungsgefahr!

Vielfach gestaltet man auch die Mutatoren auch verkettbar (s.a. Verkettung von Mutatoren).

Selbstverständlich mit einem Testfall:

Quelltext 17. Zeilen aus der Datei point30.cc [Snippet: setcolortest] 
1SIMPLETEST("Point color2") {
2    Point p;
3    if (p.getColor() != "black") return false;
4    p.setColor(100, 101, 102);
5    if (p.getColor() != "rgb(100,101,102)") return false;
6    return true;
7};

Damit haben wir eine schöne Möglichkeit, eine Linie aus bunten Punkten zu zeichnen (line.svg):

Das Programm zum Zeichnen einer sinusförmigen Punktlinie kann folgendermaßen geschrieben werden:

Quelltext 18. Zeilen aus der Datei ppc0401.cc 
 1#include <cmath>
 2#include <random>
 3#include "point30.h"
 4#include "svgfile.h"
 5#include "math.h"
 6int main() {
 7#ifdef _MSC_VER
 8    std::linear_congruential_engine<unsigned int, 31, 0, 255> generator; (1)
 9#else
10    std::linear_congruential_engine<unsigned char, 31, 0, 255> generator; (2)
11#endif
12    const int numberOfPoints {10};
13    const double scale{30.0};
14    const Point origin{1.0 * Point::svgRadius(), scale + Point::svgRadius()};
15    const double delta{2.0 * Math::mPi / numberOfPoints};
16    SVGFile file{"line.svg",
17                 Math::toInt(2 * Math::mPi * scale) + 2 * Point::svgRadius(), (3)
18                 Math::toInt(2 * scale) + 2 * Point::svgRadius()};
19    for(int i = 0; i < numberOfPoints; i += 1) {
20        const double x = delta * i;
