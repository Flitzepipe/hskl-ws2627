2. Arten der Polymorphie

Üblicherweise wird die Polymorphie in der objektorientierten Programmierung in die folgenden Arten unterteilt:

  • ad-hoc-Polymorphie

  • Inklusionspolymorphie

  • parametrische Polymorphie

Sowohl die ad-hoc-Polymorphie wie auch die Inklusions-Polymorphie sind gute Bekannte.

2.1. Ad-hoc-Polymorphie

In den meisten (objektorientierten) Programmiersprachen sind die Operatoren für die primitiven (eingebauten) Datentypen überladen. So etwa der +-Operator für die Datentypen int oder double, manchmal auch für den Datentyp einer Zeichenkette (etwa als Konkatenierung):

int x = 1 + 2; (1)
double y = 1.3 + 2.4; (2)
1 Der Algorithmus des Operators + ist auf den ganzzahligen Datentyp int abgestimmt.
2 Dieser Algorithmus des Operators arbeitet anders für Fließkommazahlen.

In C++ gehört die ad-hoc-Polymorphie elementar zur Sprache dazu: in Form von Funktionsüberladung, und zwar als

  • Überladene Operatoren für primitive Datentypen

  • Überladen von freien Funktionen

    • damit auch überladene Operatoren für UDT

  • Überladen von Elementfunktionen

    • damit auch überladene Operatoren für UDT

2.2. Inklusionspolymorphie

In den objektorientierten Programmiersprachen wird die Inklusionspolymorphie durch das sog. Vererbungsprinzip und dynamisches Binden erreicht. Ein Subtyp kann immer an die Stelle eines Basistyps treten, da er alle Eigenschaften der öffentlichen Schnittstelle des Basistyps erfüllt.

In C++ erhalten wir die Inklusionspolymorphie durch die öffentliche (public) Vererbung:

1class Base {};
2class Derived : public Base {}; (1)
3void foo(const Base&) {}
4int main() {
5    Derived d;
6    foo(d); (2)
7}
1 Vererbung
2 Das in foo(const Base&) referenzierte Objekt hat den Typ Derived.
Die private und protected Vererbung liefern keine Substituierbarkeit (ist-ein Beziehung) sondern eine Implementierungsvererbung, d.h. eine ist-implementiert-mit Beziehung.

In C++ wird bei nicht-virtuellen Elementfunktionen statisches Binden angewendet. Um dynamisches Binden (Laufzeit-Polymorphie) zu erhalten, müssen die Elementfunktionen als virtual gekennzeichnet werden (und es darf kein Objectslicing durch eine Objektkopie stattfinden).

 1#include <iostream>
 2class Base {
 3public:
 4    virtual void f() const {
 5        std::cout << __PRETTY_FUNCTION__ << std::endl;
 6    }
 7};
 8class Derived : public Base {
 9public:
10    virtual void f() const override {
11        std::cout << __PRETTY_FUNCTION__ << std::endl;
12    }
13};
14void foo(const Base& x) {
15    x.f(); (1)
16}
17int main() {
18    Base b;
19    foo(b);
20    Derived d;
21    foo(d);
22}
1 Dynamisches Binden erfolgt für virtuelle Elementfunktionen. 
virtual void Base::f() const
virtual void Derived::f() const

2.3. Parametrische Polymorphie

Die parametrische Form der Polymorphie erlaubt es nun zusätzlich, Datentypen und ihre Operationen bzw. allgemein Algorithmen unabhängig von zu ihrer Definition benötigten anderen Datentypen zu formulieren. Das bedeutet, dass Operationen bzw. Algorithmen generisch formuliert werden und führt damit zur generischen Programmierung.

Ohne die Möglichkeit einer parametrischen Polymorphie kann man zwar durch Funktions-überladung (ad-hoc-Polymorphie) polymorphe Operationen erreichen, dies führt dann aber oft zu strukturell identischem Code. Das folgende Beispiel für die Maximum-Berechnung für die DTen int und double verdeutlicht das:

Quelltext 1. Zeilen aus der Datei ppc2002.cc [Snippet: example] (einige Zeilen nicht dargestellt)
 1int maximum(int a, int b) { (1)
 2    if (a > b) { (2)
 3        return a;
 4    }
 5    return b;
 6}
 7double maximum(double a, double b) { (3)
 8    if (a > b) {
 9        return a;
10    }
11    return b;
12}
13int main() {
14    int x = maximum(1, 2);
15    double y = maximum(1.1, 2.2);
16}
1 Der Algorithmus zur Maximum-Bestimmung für den Datentyp int
2 Zur Bestimmung des Maximums zweier Werte ist die >-Relation für den Datentyp (hier int) notwendig.
3 Der Algorithmus zur Maximumbestimmung für den Datentyp double ist strukturell identisch mit dem für den Datentyp int.

Es wäre also wünschenswert, wenn man den Algorithmus zur Bestimmung des Maximums losgelöst von einem konkreten Datentyp wie int oder double formulieren könnte:

1T maximum(T a, T b) {
2    if (a > b) {
3        return a;
4    }
5    return b;
6}

Diese Form der Polymorphie erreicht man in C++ durch sog. Templates, also Schablonen. Mit ihrer Hilfe kann der Compiler bei Erfüllung aller Vorraussetzungen den konkreten Code für einen bestimmten Datentyp generieren.

Templates sind also eine Form von Code-Generatoren.

3. Templates in C++

Das obige Beispiel einer generischen Funktion T maximum(T, T) ist in C++ direkt durch Abschnitt 3.1 zu erreichen. Aber auch Klassen lassen sich durch Klassentemplates parametrieren.

3.1. Funktionstemplates

Ein Funktionstemplate ist die Schablone, aus der der Compiler auf Anforderung eine konkrete Funktion, die Templatefunktion generiert.

3.1.1. Ein einfaches Beispiel

Das obige Beispiel kann man direkt in C++ umsetzen:

Quelltext 2. Zeilen aus der Datei ppc2003.cc [Snippet: template] (einige Zeilen nicht dargestellt)
1template<typename T> (1)
2T maximum(T a, T b) { (2)
3    if (a > b) { (3)
4        return a;
5    }
6    return b;
7}
1 Template-Präambel mit T als Template-Typ-Parameter
2 Hier steht T für einen beliebigen Datentyp (T muss kopierbar sein)
3 Der Typ T muss allerdings die >-Operation ermöglichen.

Als vereinfachten Mechanismus, wie aus einem Funktionstemplate eine Templatefunktion wird, kann man sich vorstellen, dass der Compiler zunächst den sog. Template-Typ-Parameter T durch einen konkreten Datentyp (bspw. int) ersetzt. Dies führt dann zu einem zu dieser Variante identischen Code, der aber durch den Compiler generiert wird. Dieser generierte Code wird anschließend vom Compiler selbst dann auch noch übersetzt (Instanziierung).

Sprachgebrauch

Ein Funktionstemplate ist die generische Formulierung unter der Template-Präambel. Daraus generiert der Compiler eine Templatefunktion. Genauso bei einem Klassentemplate: daraus wird eine Templateklasse erzeugt.

Weil das Funktionstemplate auch mit UDT eingesetzt werden soll, folgenden wir unseren Regeln zur Rückgabe und Parameterübergabe:

Quelltext 3. Zeilen aus der Datei ppc2004.cc [Snippet: template] (einige Zeilen nicht dargestellt)
1template<typename T> (1)
2const T& maximum(const T& a, const T& b) { (2)
3    if (a > b) {
4        return a; (3)
5    }
6    return b; (4)
7}
1 Diese sog. Template-Präambel erklärt das folgende Konstrukt zum Template mit dem Template-Typ-Parameter T.
2 Weil T ein beliebiger DT sein kann, folgen wir der allgemeinen Regel zur Übernahme von Input-Parametern per const reference.
3 Hier wurde die Regel reference-in / reference-out angewendet.
4 Ebenso

Man muss beachten, dass der konkrete Typ, der für den Template-Typ-Parameter substituiert wird, auch alle impliziten Typ-Anforderungen des generischen Codes erfüllen muss.

Im obigen Bespiel bedeutet das für den Datentyp std::string, dass auch hierfür der Operator > überladen sein muss:

Quelltext 4. Zeilen aus der Datei ppc2004.cc [Snippet: string] (einige Zeilen nicht dargestellt)
1std::string z = maximum(std::string("abc"), std::string("def")); (1)
1 Hier wird eine Templatefunktion für T als std::string erzeugt,

Dies trifft für den Datentyp std::string zu, und es wird damit eine lexikographische Ordnung hergestellt.

Sollte ein Datentyp diese Typ-Anforderung jedoch nicht erfüllten, so kommt es bei der Kompilierung des aus dem Template generierten Codes zu Fehlern, wie in dem folgenden Beispiel mit einem UDT A, der den binären Operator > nicht besitzt:

Quelltext 5. Zeilen aus der Datei ppc2005.cc [Snippet: A] 
1class A {
2public:
3};
Quelltext 6. Zeilen aus der Datei ppc2005.cc [Snippet: main] 
1int main() {
2    A a;
3    A b;
4    A c = maximum(a, b); (1)
5}
1 Hier wird für T der DT A abgeleitet.
Ausgabe 1. Fehlermeldung bei der Kompilation, weil der Operator > nicht deklariert ist

ppc2005.cc:39:18:   required from here

   28 |     if (a > b) { // <> Ist `T` der DT `A` gibt es hier einen Kompilationsfehler, da der binäre Operator `bool operator>(const A&, const A&)` nicht deklariert ist.
      |         ~~^~~
Implizite Template-Typ-Anforderungen

Bei genauerem Hinsehen dieses Beispiels fällt auf, dass im Gegensatz zu dem vorigen Beispiel die Parameterentgegennahme und auch die Rückgabe per-reference erfolgt (entsprechend dem Schema: reference-in → reference-out ist erlaubt, s.a. Regel). Andernfalls (bei Übergabe / Rückgabe per-value) müsste der DT A auch noch kopierbar sein.
Ausblick

Die Fehlermeldung im obigen Beispiel ist noch recht klar verständlich. Es gibt aber auch Fälle, in denen dies nicht mehr so leicht lesbar ist.

Zudem sollte es gar nicht soweit kommen, dass eine Fehlermeldung erscheit, weil ein Datentyp eine Typ-Anforderung nicht erfüllt. Sinnvoller wäre es in diesem Fall, den Template-Typ-Parameter T einzuschränken auf diejenigen Typen T, die die operationellen Anforderungen erfüllten. Eine Möglichkeit, diese zu beschreiben besteht (ab C++-20) mit den sog. Concepts. Dieses Sprachmerkmal ist jedoch (noch) experimentell und deswegen auch nicht in allen Compilern verfügbar (in GCC ab Version 6.1 und muss mit der Option -fconcepts aktiviert werden).

Eine nähere Beschreibung erfolgt in ppcP2300.html und Concepts.

3.1.2. Definition

Wie der Name schon sagt, ergibt eine Template-Definition nur eine Schablone, aus der dann auf Anforderung konkreter Code generiert wird.

Eine Template-Definition (eingeleitet durch die Template-Präambel) ist noch kein konkreter Code! Daher definiert ein Funktionstemplate noch keine Funktion wie eine Funktionsdefinition. Auch ein Klassentemplate definiert noch keinen Datentyp wie eine Klassendeklaration / -definition.

Vielmehr definiert ein Template eine Familie von Funktionen bzw. Klassen: also strukturell einheitliche Konstrukte, die bzgl. der verwendeten Datentypen parametriert werden können (ggf. auf noch durch sog. Nicht-Typ-Parameter).
Template-Definitionen in Header-Dateien

Die Code-Struktierung in C++ ist ja beliebig, aber es ist üblich und praktikabel, dass Template-Definitionen in Header-Dateien geschrieben werden.

  • Die Header-Dateien brauchen wie üblich einen include-guard bzw. eine #pragma once-Direktive, um die ODR (one definition rule) sicherzustellen.

  • Die Template-Definition muss überall dort bekannt sein, wo das Template instanziiert (verwendet) wird. Die Header-Datei muss entsprechend inkludiert werden.

Mehrfach-Instanziierungen in unterschiedlichen Übersetzungseinheiten

Interessanterweise führen gleiche Template-Instanziierungen in unterschiedlichen Übersetzungseinheiten eines Programms nicht zu Problemen!

Haben wir das oben beschriebene Funktionstemplate max() in einer Headerdatei templates.h, die wiederum von den beiden Implementierungsdateien p1.cc und p2.cc inkludiert wird, und wird in jeder der beiden eine Instanziierung für bspw. T = int durchgeführt, so generiert der Compiler in der Tat zweimal dieselbe Templatefunktion int max<int>(const int&, const int&). Dies würde beim Binden zu Problemen führen, allerdings hat der Binder (Linker) hierfür ein Verfahren eingebaut, das mehrfache, identische Templatefunktionen entfernt.

Insgesamt führt das aber dazu, dass in jeder Übersetzungseinheit zunächst alle benötigten Template- Instanziierungen durchgeführt werden, von denen die mehrfachen durch den Binder wieder aus dem gesamten Programm entfernt werden. Dies hat natürlich einen Anstieg der Übersetzungszeit zur Folge.

3.1.3. Instanziierung: implizit oder explizit

Damit aus einem Template konkreter Code wird, muss es instanziiert werden. Für die Instanziierung müssen alle Template-Parameter bekannt sein. Man kann Templates immer durch direkte Angabe der Parameter explizit instanziieren. Bei Funktionstemplates kann der Compiler aber auch die Typ-Parameter selbst ermitteln (Typ-Ableitung), was zu einer impliziten Instanziierung führt.

Quelltext 7. Zeilen aus der Datei ppc2006.cc (einige Zeilen nicht dargestellt)
1#include "templates.h" (1)
2#include "integer.h" (2)
3int main() {
4    Integer i1{1};
5    Integer i2{2};
6    Integer i3 = maximum(i1, i2); (3)
7    Integer i4 = minimum<Integer>(i1, i2); (4)
8    double d = maximum<double>(1, 2); (5)
9}
1 Inklusion der Template-Definitionen
2 Deklaration der Klasse Integer
3 Implizite Instanziierung mit der Typableitung: T → Integer
4 Explizite Instanziierung: T → Integer
5 Explizite Instanziierung: T → double. Beachte: bei der Parameterübergabe findet noch eine Typkonvertierung von int → double statt.

Die Header-Datei templates.h beinhaltet auch die Template-Definition für minimum() (analog zu maximum()):

Quelltext 8. Zeilen aus der Datei templates.h [Snippet: min] (einige Zeilen nicht dargestellt)
1template<typename T>
2const T& minimum(const T& a, const T& b) {
3    if (a <= b) {
4        return a;
5    }
6    return b;
7}
Natürlich existieren auch in der C++-Standardbibliothek (früher auch als Standard-Template-Library (STL) bezeichnet) (s.a. Algorithmen der Standardbibliothek) entsprechende Funktionstemplates std::max und std::min.

Die Klasse Integer (integer.h, integer.cc) dient zum Test. Wichtig sind hier die beiden relationalen Operatoren <= und >:

Quelltext 9. Zeilen aus der Datei integer.h [Snippet: class] 
1class Integer {
2    friend bool operator>(const Integer& lhs, const Integer& rhs);
3public:
4    explicit Integer(int i);
5// ...
6};
7bool operator>(const Integer& lhs, const Integer& rhs);
8bool operator<=(const Integer& lhs, const Integer& rhs);

3.1.4. Typableitung für Funktionstemplates

Die Regeln zur Template-Typ-Ableitung sind recht umfangreich. Deswegen werden wir uns hier nur mit den einfachen Fällen beschäftigen.

template<typename T> void f(P x); (1)

f(expression); (2)
1 Deklaration eines Funktionstemplates f mit dem Typ-Parameter T und einem aus T zusammengesetzten Typ P für den Parameter x (etwa const T& wie oben).
2 Aufruf der Template-Funktion mit einem Ausdruck expression (des Typs E)

Der Compiler versucht nun (für jeden Funktionsparameter getrennt), den Template-Typ-Parameter T nach einigen Regeln abzuleiten. Kommt er dabei für einen Template-Typ-Parameter zu unterschiedlichen Ergebnissen, schlägt die Kompilation fehlt.

3.1.4.1. Parameterübergabe per-reference

Hier taucht P als Referenztyp auf.

Die Regel:

  • Entferne vom Typ E von expression ggf. die Referenz &, das ergibt den Typ E'.

  • Entferne vom Typ P die Referenz &, das ergibt den Typ P'.

  • Ermittle T durch den Vergleich von P' und E' unter Anwendung der Qualifikationswandlungen, d.h. Zuweisungskompatibilität unter Beachtung der const-Qualifikation

Das folgende einfache Beispiel macht das deutlich:

Quelltext 10. Zeilen aus der Datei ppc2009.cc [Snippet: example] (einige Zeilen nicht dargestellt)
 1template<typename T>
 2void f(T& x) {
 3}
 4int main() {
 5    int e1 = 0;
 6    const int e2 = 0;
 7    int& e3 = e1;
 8    const int& e4 = e1;
 9    f(e1); (1)
10    f(e2); (2)
11    f(e3); (3)
12    f(e4); (4)
13}
1 E' → int; P' → T; daraus folgt: T → int
2 E' → const int; P' → T; daraus folgt: T → const int
3 E' → int; P' → T; daraus folgt: T → int
4 E' → const int; P' → T; daraus folgt: T → const int

Zur Kontrolle die Ausgabe des Programms:

Ausgabe 2. Ausgabe des Programms: ppc2009
void f(T&) [with T = int]
void f(T&) [with T = const int]
void f(T&) [with T = int]
void f(T&) [with T = const int]

Beim folgenden Beispiel muss auf die Zuweisungskompatibilität geachtet werden:

Quelltext 11. Zeilen aus der Datei ppc2010.cc [Snippet: example] (einige Zeilen nicht dargestellt)

 3}

2 E' → const int; P' → const T; daraus folgt: T → int

4 E' → const int; P' → const T; daraus folgt: T → int

3.1.4.2. Parameterübergabe als Zeiger (per_value)

Die Regel für Zeiger-Parameter ist ähnlich:

Die Regel:

  • Entferne vom Typ E von expression ggf. die Referenz &, das ergibt den Typ E'.

  • Ermittle T durch den Vergleich von P und E'

10    f(e2); (2)
11    f(e3); (3)
12    f(e4); (4)

2 E' → const int*; P → T*; daraus folgt: T → const int
3 E' → int*; P → T*; daraus folgt: T → int
4 E' → const int*; P → T*; daraus folgt: T → const int
Ausgabe 4. Ausgabe des Programms: ppc2011

3.1.4.3. Parameterübergabe per-value, aber kein Zeigertyp

Die Regel eine Parameterübergabe per-value (kein Zeigertyp) ist ganz einfach:

Die Regel:

  • Entferne vom Typ E von expression ggf. die Referenz & und ein const (ggf. auch volatile), das ergibt den Typ E'.

  • Dann ist T derselbe Typ wie E'.

 6    const int e2 = 0;

 8    const int& e4 = e1;
 9    f(e1); (1)
10    f(e2); (2)
11    f(e3); (3)
12    f(e4); (4)
13}
1 E' → int; P' → T; daraus folgt: T → int
2 E' → int; P' → T; daraus folgt: T → int
3 E' → int; P' → T; daraus folgt: T → int
4 E' → int; P' → T; daraus folgt: T → int

In dieser Regelzusammenstellung haben wir seltene und unübliche Fälle (Zeiger per-reference) nicht berücksichtigt.

3.1.5. Funktionstemplates mit mehreren Template-Typ-Parametern

Selbstverständlich können Templates auch mehrere Template-Typ-Parameter verwenden. Diese können unterschiedlich sein wie etwa in dem folgenden Beispiel foo():

Quelltext 14. Zeilen aus der Datei templates.h [Snippet: foo] (einige Zeilen nicht dargestellt)
1template<typename T, typename U>
2void foo(T a, U b) {
3}

Oder ein Template-Typ-Parameter kann mehrfach auftreten wie etwa in bar() (oder wie oben in maximum()):

Quelltext 15. Zeilen aus der Datei templates.h [Snippet: bar] (einige Zeilen nicht dargestellt)
1template<typename T>
2void bar(T a, T b) {
3}

Auch kann man einige Template-Typ-Parameter explizit angeben während andere implizit abgeleitet werden:

Quelltext 16. Zeilen aus der Datei templates.h [Snippet: convert] (einige Zeilen nicht dargestellt)
1template<typename To, typename From>
2To convert(const From &v) {
3    return static_cast<To>(v);
4}

Natürlich müssen die Prozesse der Template-Typ-Parameter-Ableitung bei mehrfach auftretenden Parametern immer dasselbe Ergbenis liefern. Im folgenden Beispiel würde im Funktionstemplate bar() die erste Ableitung für den Typ-Parameter T den Typ int ergeben, die zweite Ableitung führt allerdings zu double!

Quelltext 17. Zeilen aus der Datei ppc2007.cc [Snippet: main] (einige Zeilen nicht dargestellt)
1int main() {
2    const int a = 1;
3    foo(a, Integer{1}); (1)
4    int i = convert<int>(2.0); (2)
5    bar(1, 2.0); (3)
6}
1 Typableitung: T → int, und U → Integer
2 explizite Angabe: To → int, Typableitung: From → double
3 Nicht möglich
Ausgabe 6. Ausgabe des Programms: ppc2007
void foo(T, U) [with T = int; U = Integer]
To convert(const From&) [with To = int; From = double]

3.1.6. Überladen von Funktionstemplates

Man kann Funktionstemplates auch überladen. In einfachen Fällen führt das auch zu den erwarteten Ergebnissen. Im folgenden Beispiel bestimmt im Grunde der Parameter y die Auswahl der Templateüberladung (s.a. die Ausgabe):

Quelltext 18. Zeilen aus der Datei ppc2021.cc [Snippet: ex1] (einige Zeilen nicht dargestellt)
1template<typename T>
2void g(T x, int y) {
3}
4template<typename T>
5void g(T x, double y) {
6}

Auch im folgenden Beispiel ist klar, dass die Variante mit dem abgeleiteten Typ vod f(T*) besser passt, weil sie weiter spezialisiert ist:

Quelltext 19. Zeilen aus der Datei ppc2021.cc [Snippet: ex2] (einige Zeilen nicht dargestellt)
1template<typename T>
2void f(T& x) {
3}
4template<typename T>
5void f(T* x) {
6}

Das kann man auch direkt sichtbar machen mit folgendem Beispiel:

Quelltext 20. Zeilen aus der Datei ppc2021.cc [Snippet: main] (einige Zeilen nicht dargestellt)
1int main() {
2    int e = 0;
3    g(e, 1);
4    g(e, 2.0);
5    f(e);
6    int* p = &e;
7    f(&p);
8}
Ausgabe 1. Ausgabe des Programms: ppc2021

void g(T, double) [with T = int]
void f(T&) [with T = int]
void f(T*) [with T = int*]

Beim Überladen von Funktionstemplates kommt das sog. partial ordering der möglichen Funktionstemplates, die aus einer erfolgreichen Template-Typ-Ableitung hervorgegangen sind, zur Anwendung. Die Regeln dazu sind allerdings vielfältig.

Das folgende Beispiel zeigt das an einem einfach Beispiel:

Quelltext 21. Zeilen aus der Datei ppc2020.cc [Snippet: example] (einige Zeilen nicht dargestellt)
 1//Variante 1
 2template<typename T>
 3void f(const T& x) { (1)
 4}
 5// Variante 2
 6template<typename T>
 7void f(T& x) { (2)
 8}
 9int main() {
10    int e1 = 0;
11    f(e1); (3)
12    const int e2 = 0;
13    f(e2); (4)
14}
1 Überladung Variante 1
2 Überladung Variante 2
3 Für Variante 1: E' → int; P' → const T; daraus folgt: T → int, Für Variante 2: E' → int; P' → T; daraus folgt: T → int
4 Für Variante 1: E' → const int; P' → const T; daraus folgt: T → int, Für Variante 2: E' → const int; P' → T; daraus folgt: T → const int

Bei Funktionsaufruf f(e1) werden die beiden möglichen Überladungen void f(const int&) und void f(int&) durch die Typableitung erzeugt. Beide Funktionstemplates werden instanziiert und anschließend findet der normale Prozess der Überladungsauflösung statt: hier wird die Variante void f(int&) ausgewählt, weil keine CV-Qualifizierung zum Parameter e1 hinzugefügt werden muss. Dies unterscheidet sich nicht von konkreten Funktionen.

Aber beim Funktionsaufruf f(e2) ist es komplizierter: hier führt die Typableitung in beiden Fällen zu void f(const int&). Dies wäre aber keine korrekte Überladung mehr. Deswegen muss jetzt vor der Überladungsauswahl noch der Prozess des partial ordering eingefügt werden: Das Template void f(const T&) ist gegenüber dem Template void f(T&) weiter spezialisiert. Deswegen wird die Variante, die aus void f(T&) entstand, verworfen.

Ausgabe 7. Ausgabe des Programms: ppc2020
void f(T&) [with T = int]
void f(const T&) [with T = int]

3.1.9. Template-Template-Parameter

Mit Template-Typ-Parametern und Template-Nicht-Typ-Parametern sind noch nicht alle Arten von Parametern abgedeckt: es fehlen noch Templates selbst, denn Templates sind weder konkrete Typen noch zur Compile-Zeit bekannte, konstante Werte. Diese weitere Art von Parametern nennt man dann konsequenterweise Template-Template-Parameter. Diese werden allerdings erst in ppcP2300.html.

3.1.10. Spezialisierungen von Funktionstemplates

Ein Funktionstemplate dient ja dazu, einen Algorithmus generisch, d.h. unabhängig von Datentypen zu formulieren. Nun kann es aber sein, dass für einen bestimmten Datentypen ein Ausnahme von dieser generischen Formulierung gemacht werden muss.

Ein Beispiel könnte unser eingangs benutzes Beispiel maximum() sein. Wird dieses für den DT std::string instanziiert, wird die lexikografische Ordnung als >-Relation verwendet.

Soll nun aber die String-Länge für die >-Relation verwendet werden, so muss eine Ausnahme vom generischen Algorithmus formuliert werden. Dies kann man mit eine Spezialisierung des Templates erreichen. Ein Spezialisierung setzt immer ein allgemeines Template voraus.

template<typename T>          (1)
void foo(const T&) {}

template<>                    (2)
void foo<int>(const int&) {}  (3)
1 Das allgemeine Template foo()
2 Die vollständige Spezialisierung (ohne Template-Parameter)
3 für den Datentyp int

Unserem allgemeinen Template fügen wir nun eine Spezialisierung für den DT std::string hinzu:

Quelltext 24. Zeilen aus der Datei ppc2026.cc [Snippet: st] (einige Zeilen nicht dargestellt)
1template<> (1)
2const std::string& maximum<std::string>(const std::string& a, const std::string& b) { (2)
3    if (a.length() > b.length()) { (3)
4        return a;
5    }
6    return b;
7}
1 Ein vollständig spezialisiertes Template hat keine Template-Typ-Parameter mehr.
2 Stattdessen wird die Parametrierung für die Spezialisierung hinter dem Templatenamen angegeben.
3 Hier erfolgt der Vergleich der String-Längen.

Der Test

Quelltext 25. Zeilen aus der Datei ppc2026.cc [Snippet: main] (einige Zeilen nicht dargestellt)
1int main() {
2    std::cout << maximum(std::string("abcd"), std::string("efg")) << std::endl;;
3}

liefert auch nun tatsächlich die längere Zeichenkette und nicht mehr die, die weiter hinten in der lexikografischen Ordnung steht:

Ausgabe 10. Ausgabe des Programms: ppc2026
const T& maximum(const T&, const T&) [with T = std::__cxx11::basic_string<char>]
abcd
Diese Spezialisierung für den Datentyp std::string diente nur zur Demonstration. Ein besserer Ansatz wäre sicherlich, dem Funktionstemplate maximum() einen weiteren Parameter für ein Vergleichsfunktionsobjekt (Callable: Funktionszeiger, Funktor oder Closure) zu geben und diesen mit einem Vorgabewert auszustatten.

3.1.11. Auflösung

Hat man (freie) Funktionen, allegmeine und spezialisierte Funktionstemplates in demselben Kontext, so stellt sich die Frage nach der Auflösungsreihenfolge, wenn mehrere Realisierungen in Frage kommen. Ausnahmsweise ist die Regel einfach: es geht vom Speziellen zum Allgemeinen. Dies ist die Reihenfolge:

  1. konkrete Funktionen ohne Anwendung impliziter Argumentkonvertierungen

  2. spezialisierte Funktionstemplates

  3. allgemeien Funktionstemplates

  4. konkrete Funktionen mit Anwendung impliziter Argumentkonvertierungen

Ein spezieller Fall entsteht, wenn man versucht, die automatische Template-Typ-Ableitung (ab C++17) einzusetzen.

Quelltext 41. Zeilen aus der Datei ppc2050.cc [Snippet: main2] (einige Zeilen nicht dargestellt)
1KVPair                   kv3{3, "ghi"}; (1)
1 Automatische Template-Parameter-Ableitung

Zwar zerfällt der Wert eines Arraybezeichners in (fast) allen Kontexten zu einem Zeigerwert (Zeiger auf das erste Element), bei der Template-Typ-Ableitung bleibt jedoch der ursprüngliche Typ (hier: char[4]) erhalten.

Im Elementinitialisierer mValue{value} hat also das Datenelement mValue den Typ char[4] während die Parametervariable value durch Zerfall den Typ const char* hat. Somit scheitert die Kompilierung.

In diesem Fall kann man wiederum eine partielle Spezialisierung für Fall eines rohen char[N] Arrays einsetzen. Dabei muss ein zusätzliche Template-Nicht-Typ-Parameter für die Länge des Arrays eingeführt werden:

Quelltext 42. Zeilen aus der Datei ppc2050.cc [Snippet: kvp3] (einige Zeilen nicht dargestellt)
1template<typename KeyType, size_t N>
2class KVPair<KeyType, char[N]> {
3public:
4    explicit KVPair(const KeyType& key, const char* value) :
5        mKey{key}, mValue{value} {}
6private:
7    const KeyType mKey;
8    std::string mValue;
9};

Möchte man bspw. verhindern, dass als KeyType auch Zeigertypen eingesetzt werden können,

Quelltext 43. Zeilen aus der Datei ppc2050.cc [Snippet: main3] (einige Zeilen nicht dargestellt)
1KVPair<const char*, std::string> kv4 {"a", "xyz"}; (1)
1 Durch die (unvollständige) Spezialisierung für Zeigertypen ist dies nicht mehr möglich.

so kann man dafür eine unvollständige Spezialisierung angeben.

Quelltext 44. Zeilen aus der Datei ppc2050.cc [Snippet: kvp4] (einige Zeilen nicht dargestellt)
1template<typename KeyType, typename ValueType>
2class KVPair<KeyType*, ValueType>;

4. Codestruktur

In den obigen Beispielen hatten wir die Defintion der Elementfunktionen eines Klassen-Templates in die Template-Definition selbst hinein geschrieben. Dies alles befand ich in einer Header-Datei. Auch eine evtl. Mehrfach-Inklusion (in unterschiedlichen Übersetzungseinheiten) mit gleicher Parameterierung war kein Problem, denn der Binder entfernt mehrfache Instanzen desselben Templates.

Allerdings ist es bei umfangreicheren Klassen-Templates unübersichlich, wenn auch die Defintionen der Template-Elementfunktionen in der Template-Definition stehen. Man kann aber auch bei Templates die Defintion von der Deklaration der Elemente trennen.

Hier zunächst die Defintion des Klassen-Templates mit der Deklaration der Elementfunktionen:

Quelltext 45. Zeilen aus der Datei heaparray01.h [Snippet: class] 
 1template<typename ValueType>
 2class HeapArray final { (1)
 3public:
 4    explicit HeapArray(size_t size); (2)
 5    size_t size() const;
 6    ValueType& operator[](size_t index);
 7    const ValueType& operator[](size_t index) const;
 8private:
 9    size_t mSize{0};
10    std::unique_ptr<ValueType[]> mData;
11};
1 Defintion des Klassen-Templates
2 Deklaration der Klassen-Template-Elementfunktion

Man hat nun wieder verschiedene Möglichkeiten, den Code weiter aufzuteilen.

Die übliche und einfachste Möglichkeit ist es, die Definitionen der Klassen-Template-Elementfunktionen in derselben Header-Datei vorzunehmen. Wie oben schon beschrieben, führt das nicht zu einer Verletzung der ODR. Es erhöht sich lediglich der Aufwand in der Compiler- bzw. Linker-Phase.

Bild 1. Code-Generierung: mehrfache identische Template-Instanziierungen werden im Programm entfernt

Die andere (unübliche) Variante ist es, nur die Template-Deklarationen in der Header-Datei zu belassen, und die Template-Definitionen in eine eigene Implementierungsdatei auszulagern. Da in den inkludierenden Quelldateien die Instanziierung nicht mehr vorgenommen werden kann, weil die Definition hier nicht inkludiert wurde, würde dies zunächst in der Linker-Phase zu undefinierten Symbolen führen. Aus diesem Grunde muss man den bestehenden Quelldateien eine weitere mit den notwendigen Instanziierungen der Templates hinzu fügen. Dies ist aufwändig und fehlerträchtig.

Bild 2. Code-Generierung: in der Quelldatei mit den Template-Instanziierungen müssen nun alle benötigten Parametrierungen vorkommen

Also schreibt man die Definitionen auch in dieselbe Header-Datei. Hierbei muss man nur berücksichtigen, dass die Elementfunktionen eines Klassen-Templates selbst wieder Funktionstemplates sind. Insofern benötigt man bei der abgesetzten Formulierung auch immer die Template-Präambel:

Quelltext 46. Zeilen aus der Datei heaparray01.h [Snippet: defs]

 2HeapArray<ValueType>::HeapArray(size_t size) : (2)
 3    mSize(size), mData(std::make_unique<ValueType[]>(size)) {
 4    assert(mData);
 5}
 6template<typename ValueType> (3)
 7size_t HeapArray<ValueType>::size() const { (4)
 8    assert(mData);
 9    return mSize;
10}
